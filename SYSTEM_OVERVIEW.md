# ASB system overview

The current ASB source version is `1.8.1`. See the [publication record](https://github.com/Jamir-boop/ASB/blob/main/docs/OPEN_SOURCE_PLAN.md) for verified release status.

ASB is a local switch board for existing Codex and Claude Desktop Code chats, including remote Code sessions observed in Claude's local cache. Its main view is a small native GNOME window. It observes local files and opens the original app. It makes no model calls.

Read [README.md](README.md) for installation, [ASB.md](ASB.md) for controls, and [Privacy](docs/PRIVACY.md) for data access. ASB uses its own version series. Agent Mission Control `0.6.0` is the upstream base, not the ASB release version.

## Runtime path

```text
scripts/asb-desktop.mjs (board launcher, never hosts the server)
  -> scripts/asb-engine.mjs startEngine, finds or starts the engine
  -> scripts/asb-native.py, GTK/Libadwaita window, with the engine URL and source token
       -> local dashboard, event, open, and ASB state APIs

src/switchboard.mjs
  -> src/app-sources.mjs, local profile registry
  -> src/codex-data.mjs, read-only Codex reader
  -> src/claude-data.mjs, Claude Desktop Code reader
  -> src/insights.mjs, root grouping and normalization
  -> PendingTracker, ASB attention and pin state

scripts/asb-engine.mjs run (asb engine run, asb service run, or asb.service)
  -> src/switchboard.mjs, loopback HTTP server in service mode through src/asb-server.mjs
  -> src/phone-gateway.mjs, optional LAN, ZeroTier, and Tailscale HTTPS listeners for the Android app
  -> scripts/asb-instance.mjs, $XDG_RUNTIME_DIR/asb/service.json, port and source token for the window
  -> scripts/asb-tray.py, Linux tray icon (StatusNotifierItem and dbusmenu on the session bus)

scripts/asb-agent.mjs (asb agent)
  -> scripts/asb-instance.mjs, safe runtime discovery and authenticated loopback requests
  -> agent status and app-source APIs of the running desktop or service

android/ (Android companion)
  -> HTTPS with a pinned certificate to src/phone-gateway.mjs
       -> allowlisted proxy to the loopback ASB server
```

The board launcher never hosts the server. It calls `startEngine`: when `findRunningService()` answers, it uses that engine. Else, when `systemctl --user is-enabled asb.service` prints `enabled`, it runs `systemctl --user start asb.service`. Else it spawns `node scripts/asb-engine.mjs run` detached, with stdout and stderr in `$XDG_STATE_HOME/asb/engine.log` (`0600`, truncated at each start). It then polls `findRunningService()` every 200 ms for at most 10 s. Without an absolute `XDG_RUNTIME_DIR`, it refuses at once with `ASB cannot start its engine: XDG_RUNTIME_DIR must be an absolute folder.` When the engine does not answer, the launcher prints `ASB cannot start its engine. See <log or journalctl --user -u asb.service>.` and exits 1. Then it spawns the Python window with the engine URL and the engine's source token in `ASB_SOURCE_TOKEN`. When the window exits, the launcher exits with the window's code; the engine keeps running. The launcher checks the engine PID every 2 s and sends SIGTERM to the window when the PID is gone, so a window never outlives its engine or keeps a stale token. An icon registration error stays visible and does not prevent the native window from opening. Launching from source (`npm run desktop` or `scripts/asb`) keeps an installed desktop entry and reports the conflict. It replaces a source-run entry, including one from another checkout. The launcher attaches only to a running ASB engine, never to another process on the port. The server binds only to `127.0.0.1`; `HOST` cannot change that. The default port is `4629`. `npm start` creates no gateway and no tray.

`asb engine run|start|stop|status` (`scripts/asb-engine.mjs`): `start` uses the `startEngine` rules above. `stop` sends `POST /api/engine/stop` through `service.json` and waits up to 10 s for the engine PID to end. `status` prints the PID, the port, and `user service` when `systemctl --user show -p MainPID --value asb.service` prints that PID, else `detached`; it exits 1 when no engine runs. Other arguments print usage and exit 2. The engine commands need Linux.

Tray: after the engine publishes `service.json`, on Linux with `DBUS_SESSION_BUS_ADDRESS` set and `ASB_TRAY` not `0`, it spawns `python3 scripts/asb-tray.py` (or `ASB_PYTHON`) with `ASB_ENGINE_PID`, `ASB_ENGINE_URL`, `ASB_SOURCE_TOKEN`, and `ASB_LAUNCHER` (`ASB_INSTALLED_LAUNCHER` when absolute, else `scripts/asb` of this checkout). The tray owns `org.kde.StatusNotifierItem-<pid>-1`, exports `/StatusNotifierItem` and the dbusmenu `/MenuBar` (Open ASB, a separator, Quit ASB), and registers with `org.kde.StatusNotifierWatcher` each time the watcher appears. Without a watcher for 60 s, it exits 0 silently. Its icon is `local.asb.AgentSwitchBoard` from the checkout's `assets/icons`. Its tooltip is `Running.` or `Running. Phone access on.` from `GET /api/phone` every 30 s. **Open ASB** and a left click spawn `ASB_LAUNCHER` without the engine variables, under systemd in its own `systemd-run --user --scope`. **Quit ASB** posts `/api/engine/stop`. The tray exits when the engine PID is gone (checked every 5 s) or on SIGTERM; the engine sends SIGTERM when it stops. A tray error prints one line and never stops the engine.

`asb engine run` and its alias `asb service run` (`runEngine` in `scripts/asb-engine.mjs`) host the server with no window. It needs an absolute, existing `XDG_RUNTIME_DIR`. It listens on `127.0.0.1` at `PORT` or `4629`, starts the phone gateway, and then writes `$XDG_RUNTIME_DIR/asb/service.json` (`0600`, folder `0700`) with `schema`, `pid`, `port`, and a random `sourceToken`. On SIGTERM, SIGINT, or `POST /api/engine/stop` it sends SIGTERM to the tray, removes that file only when the file still holds its own pid and token, stops the gateway, and closes the server. A stop request exits with code 0, so `Restart=on-failure` does not restart `asb.service`. It does not start when `service.json` is invalid or belongs to a running process. `asb service install` writes `asb.service` with `Restart=on-failure`, `KillMode=process`, and `WantedBy=graphical-session.target`, then runs `systemctl --user daemon-reload` and `enable --now asb.service`. `KillMode=process` keeps apps that ASB opened alive when the service stops. Under systemd (`INVOCATION_ID` set), each app opener runs in its own user scope through `systemd-run --user --scope`, so the app is not part of `asb.service`. Openers run with ignored stdio and a 5 s timeout, so an app that keeps running cannot hold an open request or keep the service from stopping. If the stop cleanup does not end, the engine exits 5 s after the signal or stop request with code 1, and logs the pending cleanup step and the open Node resources. `ExecStart` uses `ASB_INSTALLED_LAUNCHER` when it is an absolute executable file, else `scripts/asb` of the current checkout. Paths with whitespace, control characters, quotes, `%`, `$`, or backslashes are rejected. `uninstall` runs `disable --now`, removes only a unit file with the ASB marker line, and reloads. `status` prints `systemctl --user is-active asb.service` and whether the runtime file is valid. Other arguments print usage and exit 2. The service commands need Linux.

Engine discovery: `findRunningService()` reads `service.json`. The file must be a regular file with mode `0600` in a `0700` folder, both owned by the user. It then sends `GET /api/service` with the token and a two-second timeout, and accepts only `{ service: true }` with the same pid. An ASB `1.8.1` or older launcher has no attach mode and reports a port conflict while an engine runs.

`scripts/asb-instance.mjs` shares descriptor validation, publication, requests, and owner cleanup. It rejects linked or foreign runtime folders and unsafe files, keeps invalid descriptors, and refuses to replace one whose pid is still alive. Cleanup removes only a descriptor with the owner's pid and token. The agent CLI uses this file, then verifies `apiVersion` and pid through `/api/agent/status`; it does not scan ports or edit `sources.json` directly. The unmanaged `npm start` server has no descriptor and no usable agent interface.

Python 3 needs PyGObject, GTK `>=4.12`, and Libadwaita `>=1.4`. Node.js `>=22.13` uses built-in SQLite with read-only connections. Older supported Node.js (`>=20`) uses `sqlite3 -readonly`; the Debian package keeps that dependency. ASB's runtime has no external npm dependencies. Development tests use Node.js `>=22.13` and built-in SQLite fixtures, without the SQLite CLI.

Rust GTK/Libadwaita and Qt/C++ frontends were evaluated as unreleased `0.1.0`
prototypes, then removed with their harnesses. The [Rust comparison](docs/benchmarks/python-rust-2026-10-12.md)
found faster startup and lower frontend PSS, but mixed interaction timing and
similar repaint cadence. Both Python and Rust passed fourteen critical native
groups; [the acceptance record](docs/benchmarks/rust-acceptance-2026-10-12.md)
retains coverage and limits. The [Qt comparison](docs/benchmarks/python-qt-2026-10-13.md)
found no meaningful scroll speed gain in one valid main-monitor manual pair.
Qt had lower resize callback p95 and higher PSS, with different resize paths.
Eight bounded Qt native groups passed. These results do not prove complete UI
parity or physical display FPS. The experiments cannot be run from this tree.
Production ASB uses Python at `1.8.1`.

ASB uses `DashboardSnapshot` in `src/dashboard-snapshot.mjs` for snapshots, source events, watchers, caches, and request coalescing. It also uses local HTTP utilities, Codex open helpers, and provider cache helpers.

The current source package whitelist names 55 runtime files, including 11 ASB Bridge files, `src/phone-gateway.mjs`, `scripts/asb-service.mjs`, `scripts/asb-engine.mjs`, `scripts/asb-tray.py`, `scripts/asb-agent.mjs`, and `scripts/asb-instance.mjs`. The published ASB `1.8.1` package shipped 30 runtime files, including the app-source registry. ASB `1.8.0`, `1.7.0`, `1.6.1`, `1.6.0`, `1.5.0`, and `1.4.0` also shipped 30. ASB `1.3.0` shipped 32. ASB `1.2.0` shipped 31, down from 42 in ASB `1.1.0`.

## Sources and list scope

ASB loads enabled app sources independently. One failed source does not remove another source's rows. The default sources use these paths:

| Source | Read path |
| --- | --- |
| Codex | Latest `~/.codex/state_N.sqlite`, `session_index.jsonl`, `.codex-global-state.json`, and matched `sessions/**/rollout-*.jsonl`. |
| Claude Desktop Code on Linux | `$XDG_CONFIG_HOME/Claude/claude-code-sessions/local_*.json`, or `~/.config/Claude/claude-code-sessions/local_*.json`. |
| Claude transcript signals | Matched JSONL files under `~/.claude/projects`. |
| Claude remote Code | Session-list and watch response bodies in Claude's `Cache/Cache_Data`. |
| ASB Bridge messages | Read-only `<CODEX_HOME>/plugin-state/asb-bridge/<thread>.sqlite` files, for session messages only. |
| OpenCode | Read-only `$XDG_DATA_HOME/opencode/opencode.db`, or `~/.local/share/opencode/opencode.db`. From `session_v2`, root sessions (`parent_id is null`) with `id`, `title`, `slug`, `directory`, `time_created`, `time_updated`, `time_suspended`, `time_idle`, `idle_outcome`, `time_viewed`, and `time_archived`, and the count of subagent sessions per `parent_id`. From `session_message`, only `session_id` and `time_created`, for the last message time of each root and its subagents. |

### App-source registry

`src/app-sources.mjs` stores up to eight sources in `~/.config/asb/sources.json`, with owner-only `0600` access. XDG config overrides apply. Each source has a stable ID, provider, label, color, dot visibility, data folder, installed launcher, and enabled flag. Claude can also set a transcript folder. The three default sources (Codex, Claude Desktop Code, and OpenCode) stay registered; users can edit or disable them. Additional sources can be removed. The same physical store cannot be registered twice. Each source also has a name: the lowercase label with each run of other characters changed to `-`, trimmed, and at most 80 characters, or the source id when that is empty. ASB never stores the name: `GET /api/sources` and source write replies report it, and it does not change the settings revision. A save fails with `400` when the new name is the name or id of another source. Older settings can still contain equal names.

The OpenCode source has the ID and provider `opencode`. Its folder is fixed: `$XDG_DATA_HOME/opencode`, else `~/.local/share/opencode`. It has no launcher, because OpenCode 2 has no link that opens one session. A saved `sources.json` without it stays valid: the registry adds the default OpenCode source in memory after the saved sources, and the next save writes it. A file that already has eight sources does not get it. When the saved file has the `opencode` source, the registry replaces its saved folder with the default folder and its launcher with an empty value. A saved source with the ID `opencode` and another provider, or with the provider `opencode` and another ID, makes the file invalid. A new source with the provider `opencode` gets `400` (`Only the default OpenCode source is supported.`). An edit of the OpenCode source that changes the folder or sets a launcher gets `400`. Name, color, dot, and the enabled flag can change.

A Codex source reads its `CODEX_HOME` folder with the same relative files as the default source. A Claude source reads its app profile folder, including `claude-code-sessions` and `Cache/Cache_Data`; its transcript folder defaults to `~/.claude/projects`. This supports separate profiles that use one app binary with isolated `CODEX_HOME` and Electron profile folders. On the first registry read, when `sources.json` is absent, ASB registers the known ChatGPT Personal profile only if its local store and installed launcher are present. ASB does not change logins, credentials, app data, or default URL handlers. ChatGPT-labeled sources expose local Codex coding chats; ordinary ChatGPT cloud chat history is outside this source.

Default sources keep their existing row IDs. Additional sources prefix row and parent IDs with the stable source ID, while `externalId` keeps the original app ID for opens. Equal app IDs in different stores remain separate. Rows provide `sourceId`, `sourceLabel`, read-only `sourceColor`, and `sourceShowMarker`. The compatibility fields `sourceNumber` and `sourceCount` remain metadata; numbers are not visible. Numbers start at one per provider in registry order, including disabled sources. Removal can change numbers, but source IDs define identity. Colors do not merge sources or chats. Disabling or removing a source does not delete ASB attention, pins, unread marks, or settings.

Source settings schema `1` accepts optional `color` as a six-digit hex value and saves it in lowercase. Old settings without a color get a stable default from the source ID. An edit that omits `color` keeps the existing color. Dark picker colors also save; native rendering adjusts only the displayed color to keep 3:1 contrast on the current base and hover backgrounds. Optional boolean `showMarker` defaults to true for old settings. An edit that omits it keeps the existing value. False hides only the profile dot in both views; color, source reads, opens, state, unread, and pins stay unchanged. The native editor uses explicit Save and shows save success or errors.

`appSourcesRevision` hashes ordered, normalized source settings into an opaque 64-character lowercase hex revision. Counts, provider status, and other report fields do not affect it. `GET /api/sources` returns `revision`; the dashboard returns `sourcesRevision` from the exact source configuration used by its scan. The revision is not stored in `sources.json`, which remains schema `1`. Update and Remove check an optional quoted `If-Match` revision inside the registry's serialized write queue after reading current settings. A stale revision gives `409` with no write; a malformed header gives `400`. Older clients without the header keep their existing behavior.

Additional profiles need a supported installed launcher path. ASB sends that launcher one validated app URI through detached `spawn`, without a shell. The launched app runs independently after dispatch; ASB does not wait for or stop it. Default sources can leave the launcher empty to use the existing URL handler. Each profile's files and directories use the shared debounced watchers and existing polling fallback.

Root chats are the list unit. Explicit workers and subagents stay grouped under the root. ASB omits `subagent` and `guardian_review` source rows. Each source has a 5000-record limit. ASB does not discover orphan Codex rollouts outside the database. Archived rows are available but hidden by default.

Codex names prefer the desktop/session-index name, then the raw stored title, with the existing empty fallback. ASB does not select `first_user_message` for title derivation. A row title is limited to 300 characters; a longer title ends with `…`. Whole Unicode code points are kept. Codex stores can hold a full prompt as a title. Search and the tooltip use the limited title. Claude Desktop Code titles keep their own shorter limit. Claude metadata must have a valid `local_<uuid>` ID to provide an open action. App links are constructed from valid IDs:

- `codex://threads/<uuid>`
- `claude://code/continue?session=local_<uuid>`
- `claude://code/<validated cse_ or session_ ID>`

Default app opens use the source apps' registered URL handlers. Registered profile launchers receive the same validated links. ASB does not create chats or run a CLI resume command for its open action.

Remote cache reads accept only production `https://claude.ai/v1/code/sessions` and `/watch` response bodies. They accept any query parameters on these two paths, because the Claude app adds new ones (for example `keepalive_tolerance_seconds`). `resume_token` gives the start cursor. HTTP headers, credentials, transcript-event endpoints, and raw account/config fields are not used. Completed cache entries use Chromium stream boundaries; open gzip watches use their partial body and zero-filled reserved tail. ASB selects the newest response and exact cursor-linked continuations, not a union of old login streams. Missing full-list metadata produces a source warning and only observed rows. Cache delay, eviction, and offline periods can limit coverage. No remote request is made.

Local bridge aliases deduplicate matching remote rows. For bridge records, validated `session_<token>` and `cse_<token>` links use the same identity. ASB keeps the local row, folder, and direct-open link. Invalid aliases and aliases with more than one local owner cannot remove a remote row. Cloud rows require an exact stored alias. Titles and times do not establish identity. Aliases stay outside the view payload.

Remote execution requires a response observation within six hours plus explicit worker/session state. Server sync receipt cursors provide observation time; file modification time is a fallback for an approved body write. Bridge sessions also need an explicit connected state. Cloud sessions do not need that bridge field. Unknown, stale, or disconnected records give Unknown. Remote Working has no inferred start time. Folders stay empty; safe Git source names can identify a project. Fresh cached unread marks use the same ASB attention rules as other native marks.

### Session messages

The dashboard has the top-level list `messages`: `[{ from, to, atMs }]`. Each entry is one message that one chat row sent to another in the last two minutes. `from` and `to` are row IDs, and `atMs` is a time in milliseconds. The native window animates these entries. The list is always present. It holds at most the newest 50 entries, sorted by `atMs`, then `from`, then `to`. Exact duplicates are removed.

ASB uses receiver-side records only, so each message counts once. There are two sources:

- Claude transcript: each incoming message has one delivery record. The first form is a meta `user` record whose text has the `<cross-session-message` opening tag in its first 200 characters, after one plain system line. The second form is a `queued_command` attachment whose string `prompt` starts with the tag. A tag after other markup, for example in a task notification, does not count. A `user` record that is not meta, or an array prompt, does not count. The reader parses only the opening tag. The sender is `from-session` when it is `local_<uuid>` or a UUID. Otherwise it is `from` when it is `local_<uuid>` or `bridge:session_<token>` or `bridge:cse_<token>`. Other records are ignored. The lifecycle state keeps the last 20 senders and record times in file order. Thus an incremental read and a full read give the same list, and the full lifecycle scan of a large transcript also collects them. Desktop threads get `incomingMessages` and `priorCliSessionIds` from the metadata. Remote cache threads get neither field.
- ASB Bridge database: `readBridgeMessages` in `src/codex-data.mjs` lists `<CODEX_HOME>/plugin-state/asb-bridge/`. The file name is the receiving Codex thread ID. A file whose newest time (main file or `-wal`) is older than the window is not opened. The reader checks the `messages` columns, then selects only `peer_id`, `status`, `created_at`, and `kind` (when present) of `in` rows inside the window. It keeps the statuses `accepted`, `started`, and `steered`, and only `kind = 'message'` when the column exists. `peer_id` must be a UUID. `created_at` is in seconds. A per-file cache signature includes the `-wal` stat, because a WAL append does not change the main file. A read error skips only that file. `loadCodexDashboard` attaches `incomingMessages` to the receiving thread.

`resolveSessionMessages` in `src/switchboard.mjs` maps native IDs to row IDs across all sources. Codex rows use the thread UUID. Claude rows use `local_<uuid>`, `cliSessionId`, each of `priorCliSessionIds`, and `bridge:session_<token>` and `bridge:cse_<token>` for each bridge alias. Remote Claude rows use the same two `bridge:` keys. A thread that is not a row, such as a Codex subagent, resolves to its root row. A key with two different rows is not used. ASB keeps a message only when both rows are on the board, the sender is not the receiver, and the time is in the window (up to five seconds in the future). Rows never get `incomingMessages` or `priorCliSessionIds`. The payload has no message text, sender name, or address. No new watcher is added: the normal refresh (two seconds while Working, else five seconds) reads new messages.

These messages are not shown: messages to a session that is not a card (a CLI-only session or a remote receiver), messages between subagents inside one session, and messages written in an old CLI transcript of a chat.

### Usage limits

Each row has the number `limitResetsAtMs`, a time in milliseconds. It is greater than 0 only when a usage limit stopped that session and the reset is still in the future. Else it is 0. The native window greys out such a card and shows "Resets in" with a countdown. There are two sources:

- Codex rollout: a full window does not stop a session, because an account with credits keeps working past it. The stop is the end of the turn: a `task_complete` record whose `error` is an object with `codex_error_info` `usage_limit_exceeded`. Other `codex_error_info` values (for example `cyber_policy` and `server_overloaded`) are not limits. ASB never reads `error.message`. Codex can refuse the next request before a window shows 100 percent (the last window record often shows 94-98 percent), and the failed turn writes one more `token_count` with `rate_limits.limit_id` `premium` and `primary` and `secondary` null. The rollout lifecycle (`applyRolloutLifecycleEvent`) keeps three values. The stop flag: `task_started` clears it, that error sets it, and any other turn end clears it. The stop also keeps its `task_complete` time `limitStoppedAtMs` (cleared with the flag). The window record: for each `token_count` with at least one non-null window object (`rate_limits.primary` or `rate_limits.secondary`), `limitWindowAtMs` is the record time and `limitWindows` keeps each window as `[used_percent, resets_at (in seconds) times 1000]`. It stays across turns. A `token_count` with no window (for example `premium`) changes nothing. Plus accounts have a 300-minute primary and a 10080-minute secondary window. Pro accounts have only a 10080-minute primary window, so a reset can be up to 7 days away. `rate_limit_reached_type`, `limit_name`, `credits`, and `plan_type` are not used. The thread gets `limitResetsAtMs` when the latest turn ended with the stop and the window record is at or before the stop. `limitStopResetsAtMs` then takes, among the windows of that record that reset after the stop and show 90 percent or more (`LIMIT_STOP_USED_PERCENT`), the most-used one (highest `used_percent`; on a tie the later reset). With no such window it gives 0. So a full 5-hour window that reset before the stop gives way to a full weekly window, and a low snapshot (for example from usage on another machine) cannot give a false reset days away. An old reset that a later retry stop leaves in the log does not count, because only a reset after the stop counts. When the tail has the stop but no window record, the reader scans the full log for the newest window record. The lifecycle scan parses a `token_count` line only when its raw text has a `used_percent` number, so other lines are skipped with one regular expression test. A retry turn can fail at once with no window record. `loadCodexDashboard` then sets the reset of each stopped thread from the newest window record at or before its stop, chosen among its own record and the records of all threads of the same Codex home (the own record wins a tie), with the same window rule. A newest record that fails the rule gives 0; an older record is not tried. A stop with no known reset gives 0. `limitWindowAtMs`, `limitWindows`, and `limitStoppedAtMs` are internal thread fields and are not on the rows.
- Claude transcript: the lifecycle state (`applyClaudeLifecycle`, which also runs in the full lifecycle scan of a large transcript) keeps the limit. An assistant record with `isApiErrorMessage: true`, `error: "rate_limit"`, and a number `quotaLimits.resetsAt` (in seconds) sets it. A new human prompt, a task start, or a later assistant record that is not such an error sets it to 0. Desktop threads get `limitResetsAtMs`. Remote cache rows get 0.

`buildSwitchboardDashboard` gives a row the thread limit only when it is after `nowMs` and the row is not Working and not Waiting with a required action. The state of a limited row stays Idle. `PendingTracker.apply` treats a limited row like a Working row: `unread` is false, it is not Pending unless it has question attention or a required action, and `pendingSource` is empty. Stored marks do not change; they show again after the reset. The reset times are in the expiries of `nextStatusCheckAtMs`, so ASB builds the cached dashboard again at the reset.

Limits: a Claude limit record without `quotaLimits` (model limits and the older text form) gives no limited state. ASB does not parse the message text. Only the session that the limit stopped is limited, not every session of the profile.

## Execution and attention

Execution uses Working, Waiting, Idle, and Unknown. A root is not Working only because it is unarchived. Open task/request signals require activity within six hours. Source signals can lag or survive a crash; old open signals become Unknown.

Codex roots include unarchived descendants with explicit database links, including nested subagents. The existing bounded rollout cache reads their lifecycle. A recent open child task keeps the root Working after the root's own task ends. Only recent open members set the current start time. Missing or stale child lifecycle gives Unknown unless another member has current work. Archived, unrelated, and orphan rollouts do not change root execution.

The Claude Desktop Code reader includes child files under the matched root transcript in the child count. An async Agent launch links its returned agent ID to the child file `agent-<agentId>.jsonl`. The reader uses the file in the `subagents` folder of that exact root first. The desktop app can give a chat a new CLI session ID, and then the child files stay in the folder of the old ID. Thus, when the root's own folder does not have the file, the reader uses the file that is directly in the `subagents` folder of another session in the same project folder (the folder that holds the root transcript). With more than one such file, it uses the one with the newest current `mtimeMs`. It never uses a file from a different project folder. The child count includes only the root's own files. A background workflow has a different link. Its launch result is the result of a `Workflow` tool call with the status `async_launched`, a `taskId`, and a `runId`; it has no agent ID. The key of the link is the `taskId`, and the link keeps the `runId`. The run writes its logs (one `agent-<id>.jsonl` for each workflow agent, and `journal.jsonl`) to the folder `subagents/workflows/<runId>` of a session folder. These logs have no end record. Thus the link is open work when at least one `.jsonl` file directly in that folder has a current `mtimeMs` at or after the time of the launch call; the newest such `mtimeMs` is the activity time. The reader uses the run folder of the root's own session folder first. When the root has no such folder, it uses the folder with the same `runId` in another session folder of the same project folder, and never one in a different project folder. With no folder, or with no file at or after the launch call, the work of the link is unknown. Only the task notification with the `taskId` closes the link. A resumed run has a new launch result with its own `taskId`, so it is a new link. The files of a run are not in the child count. A `SendMessage` result with `success: true` and a valid `resumedAgentId` opens the link of that subagent again, or creates the link when the launch is not in the transcript. In the child transcript, the message that starts an ended subagent again is a meta `user` record with `isSidechain: true`; it starts a task when the child has no open task. A meta record in a root transcript starts no task, except a message from another session in an idle chat (below). The summary record of a context compaction (a `user` record with `isCompactSummary`) is not a prompt. It starts no task and does not change the start time of the open task. The app writes the records of the open turn after the summary with older timestamps, and these records stay in order because the summary does not move the event time. An assistant record that has a `tool_use` block is not the end of a turn, also when its stop reason is `refusal`, because the app runs the tool. A task notification has two record forms in the root transcript. The first form is a `user` record whose string content starts with `<task-notification>`; its `timestamp` is the delivery time. The second form is an `attachment` record with `attachment.type` `queued_command` and the notification text in the string `attachment.prompt`; the app uses it when the chat is busy. The `timestamp` of the second form is the end of the task, not the delivery time, so the record can come after records with a newer timestamp. In each form, a notification with the status `completed`, `failed`, `cancelled`, `aborted`, `stopped`, or `killed` closes the link, but only when its timestamp is not before the launch or resume time of the link. `completed` gives a completion, `failed` gives a failure, and the other statuses give a cancellation. A notification without a `<status>` tag closes no link. The first form is also a prompt: the app runs the model on it, so it starts a task like a human prompt (also for a task that is not linked). It starts no task when its status is `stopped` or `killed` (these usually get no reply) or when the record has `queueTranscriptOnly: true`. Thus a linked failed or cancelled notification at an idle root does not end the group at the notification; the end of the reply turn sets the outcome. The reply turn continues the task of the prompt for Discard: it sets the Working timer start but not `latestTaskStartedAtMs`, so a Discard armed while the background agent ran stays armed and applies to the end of the reply. An `attachment` record changes nothing else, and `queue-operation` records are ignored. The child log writes its end 0.1 to 2 seconds before the notification reaches the root. Thus an open link (no notification yet) whose child log has ended counts as open work for 10 seconds after the child end (`CLAUDE_CHILD_END_GRACE_MS`), with the child end as its activity time. The thread field `childEndGraceAtMs` (internal, not on the rows) is the earliest such grace end, and it is in the expiries of `nextStatusCheckAtMs`, so ASB builds the cached dashboard again when the grace ends. After the grace, the child end counts as before. A lost notification thus gives at most about 10 seconds of Working. Recent child request, thinking, and tool events keep the root Working after its own response ends. Child completion, interruption, and error events close that work. Unrelated children cannot change execution. Missing linked lifecycle gives Unknown unless the root has current work. Stale child work cannot set a fresh root's timer start.

Each non-empty Claude user reply starts a task, including `ok`, `y`, `1`, `.`, and `继续`. A user record that is not meta and has an image item and no `tool_result` item (a prompt with only images) also starts a task. A message from another session (the meta `user` record form in [Session messages](#session-messages), when `crossSessionSender` accepts it) starts a task only when the root is not running; during a running turn it does not move the start time. Background Bash (`run_in_background`) and Monitor tasks are not linked: the model is idle while they run. Local command records (`<local-command-caveat>`, `<command-name>`, `<local-command-stdout>`) do not start a task. Both readers skip a JSONL line that is not an object.

Current synchronous questions can block execution in Waiting. Async questions add attention while Working or Idle remains visible. Matching answers, failure, abort, or cancellation resolve the question. Real human input supersedes old questions. Automatic goal continuation, context, and partial answers do not. Question and answer bodies stay outside ASB view payloads.

A pending Claude `AskUserQuestion` tool call is a question. It gives Waiting and question attention. If it is the only pending tool and a linked child has recent open work, the row stays Working with question attention. The Claude Desktop app can end a turn with the `mcp__ccd_turn__wrap_up` tool. The tool result ends the turn as `task_complete` (also in the lifecycle-only scan of a large file). The model can still write records after it: usually an `end_turn` text and a `stop_hook_summary` within seconds, sometimes more tool calls. Some turns have no later end record. Later ends keep the question, and an active assistant record clears it. When the wrap-up input has a non-empty `ask`, ASB records a pending `AskUserQuestion` under the key `wrap-up:<tool use id>`, so the same question rules apply. No tool result clears it: the next root turn start (a human prompt, a delivered wake, `task_started`, or an active assistant record), a cancel, a failure, or a result clears it. ASB keeps only whether `ask` is non-empty, never the ask text, the recap, or the actions. A wrap-up without `ask` is a normal completion. Other pending permission tools, including `ExitPlanMode`, give Waiting with a passive `?` until a tool result or terminal event resolves them. A pending Claude permission, plan approval, or question tool gives Waiting and Pending only for six hours after its tool event. After that, the usual rules apply, and an old open task gives Unknown. A fresh remote worker `requires_action` uses the same wait rule. Ordinary Bash, Edit, Write, and MCP permission prompts write no transcript record. On each Claude load, ASB reads the live Claude session registry (`<config>/sessions/<pid>.json`, next to the transcript folder) through `src/claude-registry.mjs`, the same reader that `asb agent peers` uses. A record counts only when its file is owned by the user, its pid is alive, and `/proc/<pid>/stat` has the recorded start time. A record whose `hostSessionId` is the Desktop session ID matches first; otherwise its `sessionId` must be the CLI session ID or a prior one. The newest `statusUpdatedAt` wins. Only `status` `waiting` changes the row: it is a permission wait with Waiting and Pending, or, for `waitingFor` `input needed`, a question with question attention. Other statuses leave the transcript state unchanged, and each load starts again from the transcript, so no live wait stays. These fields were observed in Claude Code `2.1.299` and are not a published API, so this is best effort: a missing or unreadable registry changes nothing. ASB does not cache the registry; a watcher on the registry folder starts a new scan when a record changes. ASB Read and successful opens cannot clear these waits. The Read control has no Read action during such a wait, and the **Unread** switch of the row panel is insensitive; Pin stays available.

OpenCode rows come from `loadOpenCodeDashboard` in `src/opencode-data.mjs`. Only `session_v2` root sessions are rows; subagent sessions add to the root's `subagentCount` through `embeddedSubagentCount`. The title is `title`, else `slug`. The execution claim (`time_suspended`) sets `lifecycleRunning` and the task start. The newest `session_message.time_created` of the root and its subagents is the activity time, else the claim time. So a claim with a message in the last six hours is Working, an older claim is Unknown, and no claim is Idle. `idle_outcome` `succeeded`, `failed`, and `interrupted` map to `task_complete`, `failed`, and `turn_aborted` at `time_idle`: Done, Failed, and the stop square with no attention. Native unread is `time_idle > (time_viewed or 0)`; no `time_idle` gives unknown read status. OpenCode keeps permission asks and questions only in memory, so OpenCode rows have no Waiting and no question attention. Rows have `providerLabel` `OpenCode`, `canOpen: false`, and no app link; `openSwitchboardThread` refuses them with `OpenCode cannot open one session from a link.` A missing database gives the `missing` status. A database without `session_v2`, `session_message`, or a needed column gives the warning `ASB reads OpenCode 2 sessions only. Update OpenCode.` and no rows.

Codex approval wait is unsupported. The local state schema has no current unanswered approval field, and the examined rollout schema has no reliable request/resolution pair. ASB does not read the app-server `waitingOnApproval` flag or infer approval from tool names, time, or policy fields. An open task keeps its current Working rule.

Linked Codex child questions add root attention. A current synchronous child question gives Waiting when no recent open member can continue. The root's own current synchronous question keeps its Waiting priority. Native read status still comes from the root. ASB Read acknowledges group attention without changing source questions or read marks.

Pending is separate from execution. Every visible unread dot or `?` counts as Pending, including Unknown and archived rows when they have a visible dot. A stop square does not count as Pending. A Working chat cannot be unread. While a row is Working, `unread` is false and only question attention makes it Pending. Stored manual, native, completion, failure, and retained marks do not change; they show again when Working ends.

Native Codex unread needs a creator identity and exact local host match. Missing or unmatched metadata gives Unknown read status. Identity fields stay outside the API. Local Claude chats have no reliable native unread source. ASB completion and failure marks require an observed Working-to-Idle change and a new terminal event. A task that goes Working, Waiting, then Idle keeps this observation and gets its completion or failure mark. Historical Idle rows do not gain either mark on first load. Sources with native read truth keep their native rule. Abort and cancellation add no new unread mark.

Codex and Claude terminal attention is held until the root and its linked child work end. The last group end sets the outcome. A successful end can add completion attention. A failed end can add a failed-task dot until Read, under the same observed-end, open acknowledgment, and Persistent unread rules. Codex failure uses a non-null terminal `task_complete.error`. Claude failure uses terminal `result.is_error`, a linked failed task notification that ends the group (a queued or transcript-only copy; a delivered notification starts a reply turn whose end sets the outcome), or a fresh remote session `failed` state. Linked child task notifications handle the statuses `completed`, `failed`, `cancelled`, and `aborted`. Ordinary tool errors, refusal text, child shutdown, and interruption do not establish task failure. A later completion or cancellation takes priority over an older failure. Child IDs, error bodies, prompts, and transcript paths stay outside the ASB view and state file.

A final root or group cancellation gives Idle with a passive stop square, including historical rows. Read does not clear this source outcome. New work or a later end removes the square. Existing question or unread attention remains visible in preference to the square.

Discard applies once to the current Working task. A verified successful root/group end clears the arm and suppresses its completion and matching native unread attention, including new Persistent unread retention. It does not clear manual Unread, question attention, or earlier failed-task attention. Failed ends keep their normal dot; cancellation keeps the stop square. Discard is not attention and does not change state or sort order. Any observed Idle clears the arm. Waiting and Unknown keep it stored.

Existing lifecycle caches retain explicit member starts and terminal timestamps/kinds. The tracker uses these signals through private row Symbols, without exposing identities or transcript paths. A root ending while a linked child continues does not clear Discard. A child's first start uses explicit Codex creation or Claude launch/request evidence to cover late starts; missing evidence remains conservative. A proven new root task after its terminal event clears the old arm, including when Idle was missed between scans. A verified group end followed by new member work also clears it. A follow-up message in an armed Claude task does not clear the arm. Only a task that starts after an end later than the arm clears it. The displayed Working timer is not a task identity.

The first matched native unread episode for a discarded success is acknowledged locally, including a mark that arrives one scan later. A later observed Read-to-Unread cycle is preserved. The first late mark cannot be distinguished from a source-app manual Unread for the same completion; that first episode can be suppressed. A verified newer end clears the old native mask, and a failed end cannot use it. Local readers keep only the latest terminal data: if an armed task and a whole later task both end before the next observation, the later successful end can be discarded. Discard arming therefore scans current source state and rejects an already-Idle row; Keep uses the normal cache. This prevents a late cached click from arming after both tasks ended. Remote `completed`/`review_ready` and `failed` terminal metadata are supported. Generic remote Idle without a terminal timestamp clears the arm but does not suppress unknown/native attention. A remote end and new run wholly between observations cannot be proved from the cache metadata, so the old arm can remain. ASB makes no timing guess or remote call.

Mute (`PendingTracker.setMuted`, record field `muted`, row field `muted`) is per session. In `observe()`, a muted success is a scan where the row is muted, Idle, and not archived, its completion is newer than `seen`, and the end is not a failure (the task kind is not `failed`, and `failedAtMs` is not newer than `completionAtMs`). A muted success takes exactly the discarded-success path: `discardedAt` is the task end, `discardNative` is reset, the pending mark is acknowledged unless it is a failure, a retained `native-unread` or `observed-completion` source is cleared, no new pending mark is set, `seen` and `drawerSeen` move to the end, and the native unread of that task is suppressed, also when it arrives in a later scan. So completion attention, native attention, the Done sound, and the Done phone notification stay off. Failures, questions, permission waits, manual Unread, and the drawer rules do not change. Mute applies only to tasks that end after it is on; turning it on clears no dot. A later muted success clears an older success dot but not an older failure dot or manual Unread. The native menu has no Discard result for a muted row; a Discard armed before Mute stays.

The drawer holds unread rows that the user wants out of the way. Only a row with an unread dot can go in. A row with question attention, a required action in the original app, or a Working state cannot. In the dashboard, a drawer row has `drawer: true` and `unread: false`. It is not Pending and sorts with the read rows. The drawer has no time limit. The row leaves in these ways: take out; Read; Unread (through the API; in the row panel of a drawer row, **Unread** and **In the drawer** are on, and turning off either one reads the row or takes it out); a successful open when Persistent unread is off; new attention; or no stored mark is left. With Persistent unread on, an open keeps the marks and the row stays in the drawer. The tracker saves `drawerSeen`, the newest result time that ASB had seen for the chat when the row was put in the drawer. The row comes out as normal unread and Pending when ASB sees a result or failure time that is newer than `drawerSeen`, or when the chat has a question. This includes a task that ASB did not see in its Working phase, for example a short task between two scans. A native unread that is raised again in the original app with no new result does not take the row out. When no stored mark is left, for example the chat was read in the original app and ASB has no other mark for it, the row leaves the drawer as a read chat. An unknown native read state for a time keeps the row in the drawer. A drawer row that goes Working stays in the drawer. A stopped task keeps the row in the drawer. A task that ends with Discard result on acknowledges the completion and native marks, as in 1.5.0. A drawer row whose only mark is of that kind is then read and leaves the drawer. A drawer row with a manual Unread mark stays in the drawer and is not Pending. The drawer changes nothing in Codex or Claude.

Read, Unread, pins, pin order, and the drawer belong only to ASB. A successful open acknowledges ASB attention when Persistent unread is off. It does not change execution or answer a question. Failed opens preserve attention. Persistent unread retains native, completion, and failure attention until Read, even after source Read or successful opens. It does not retain question attention: a resolved question leaves no mark, and a stored `user-question` retained source from an older version loads as none. It is on by default when the saved setting is absent or non-boolean. An explicit saved false stays off.

All clients share one tracker. Tracking uses the complete scanned list before filters. `pending.json` contains IDs, marker/acknowledgment values, manual marks, retained sources, pin order, Persistent unread, numeric Discard fields (`discard`, `discardedAt`, `discardStart`, `discardEnd`, `discardNative`), two numeric drawer fields (`drawer`, 0 or 1; `drawerSeen`, the newest result time that ASB had seen for the chat when the row was put in the drawer), and the Mute field `muted` (0 or 1; any other value loads as 0). Version 1 remains compatible with old records, and files from `1.5.0` load as they are; missing/invalid numeric fields use zero. The file has owner-only access. It contains no chat titles, message bodies, call IDs, or transcript paths.

ASB shows the Pending state warning when it cannot use `pending.json` in full. The causes are an unreadable file, invalid JSON, a version other than 1, a bad shape, or a dropped record. ASB then moves the old file to `pending.json.bad` before the first save. An older `.bad` file is replaced. The same rule applies to `sources.json`: ASB moves it to `sources.json.bad` before the next source update or remove. The warning that ASB cannot save Pending state clears after the next good save.

### Sounds

The ASB server plays a sound on the PC for Done, Needs input, and Failed. It uses the same rules as the Android notifications (`notify/Events.kt`). `src/asb-sounds.mjs` checks the dashboard root rows after `PendingTracker.observe`. Done is completion attention, or native attention on an Idle row (a Codex chat with native read state) whose last outcome is not `failed`. Failed is failure attention, or such native attention with the last outcome `failed`. Needs input is question attention or a required action. An archived row has no events. Only a bit that is newly set since the previous update plays. A row that is missing from one update keeps its old bits. While a row has a usage limit, or had one at the previous update, only Needs input plays. The first dashboard after start only sets the baseline.

Each dashboard update plays one sound at most: Needs input, then Failed, then Done. The files are in `assets/sounds/`. They have the Android file names, but they are louder copies (a gain of 8 to 19 dB and a limiter at about −1 dB peak), because the original opencode files are too quiet on PC speakers: `opencode_staplebops_01.mp3` (Done), `opencode_staplebops_02.mp3` (Needs input), and `opencode_nope_03.mp3` (Failed), with `opencode-LICENSE.txt`. The player runs `pw-play --media-role Notification -P '{ application.name = "ASB" }' <file>` detached. The PipeWire node has `application.name` ASB, but GNOME lists the stream as `pw-cat` (an event sound), because GNOME takes the name from the client. Its volume follows the System Sounds volume. If `pw-play` is missing, ASB uses `paplay --client-name=ASB --property=media.role=event`. If neither exists, ASB plays no sound and writes one log line. The dashboard path never waits for the player.

The sounds run in the one ASB server process: the engine or `npm start`. The engine (`serviceMode`) plays a sound only while a native window has sent a UI report (`POST /api/agent/ui`) in the last 45 s (`server.boardOpen()`). A window reports at least every 25 s, so sounds can continue for up to 45 s after the last window closes. The watcher moves its baseline also while it is silent, so a window that opens later plays only new events. The `npm start` web view sends no UI reports and keeps its sounds. `createSwitchboardServer` plays sounds only when the caller passes `playSound`, so tests and other imports stay silent. There is no sound setting. The phone keeps its own sounds.

## Refresh and performance limits

Native and web clients poll every two seconds while any unarchived root is Working, otherwise every five seconds. This uses the full list before filters and continues when ASB loses focus. The clean server snapshot has a five-second TTL. With two-second polling, reconciliation can occur on the next tick after about six seconds. Cold scans and source write delay can take longer.

Source watchers send only a version, reason, and provider flags. They send no paths or content. Registered source folders and registry changes use these same watchers. Events are grouped for 250 milliseconds. Active scans start no more than once per two seconds. Missing directories and failed watches retry every five seconds, only for the affected required or optional roots. Healthy watcher trees stay in place. A required root failure keeps coverage incomplete; polling remains the fallback. Late callbacks from closed or replaced watchers are ignored. On Linux, ASB uses one watch for each directory under the session folders, not one for each file. It follows new and removed folders from `rename` events, with one `stat` for each event entry. Full directory walks remain for start, changed watch paths, root replacement or structure invalidation, a burst of more than 64 structure events, and the 60-second safety check. A watcher error retries its affected root. `performance.dashboard.watchWalks` counts directory walks, including recovered subtrees; a simple absent-root check does not increment it. Other platforms use the native recursive watch and fall back to directory watches. An injected `loadDashboard` with no source registry gets no default watch paths. Profile registration adds no permanent fast poll.

In service mode (`serviceMode: true`), the server scans with no client. After it listens, it loads the shared dashboard, then schedules the next scan after two seconds while any unarchived root is Working, otherwise after five seconds. A source event with no connected event client also starts the follow-up scan. In this mode the clean snapshot lasts only one scan interval, also with full watch coverage. So ASB sees each task end while the window is closed, and the phone can show Done notifications on its next read. Close stops this timer.

Client reads do not overlap and retain at most one requested follow-up. A forced read (`/api/dashboard?force=1`) that arrives during a scan waits for that scan. It then gets one more scan that starts after the request. Forced requests during the same scan share that scan. A successful open marks the server snapshot dirty and sends a `dashboard` event with the reason `asb-open`; the next read scans again. Successful native session actions request a normal queued refresh and retain a follow-up if a read is already active. The Discard server action still forces its validation scan before arming. Successful opens in both clients use the normal refresh path. Each `200` reply of `GET /api/dashboard`, with or without `?force=1`, has an `ETag` header: a quoted SHA-256 content hash of all reply fields except `generatedAtMs` and `performance`. The dashboard replies also have `Cache-Control: no-store`. A request with `If-None-Match` equal to the current tag gets `304` with no body; a forced request still scans first. `performance.dashboard.notModified` counts these replies. Both clients send the tag of the dashboard that they show in `If-None-Match` and skip list updates on `304`. The native window clears the tag after an error and after a POST reply changed its list. The browser clears its tag after an error; a queued forced browser refresh remains forced. Native rows remain keyed by ID and update in place. Rows skip unchanged cached text and action updates. A lazy row cache retains previously shown rows across search and filters, bounded by full dashboard IDs. Hidden rows have no clock work or Read feedback; current data, action state, time, view, and palette apply when they return. Layout signals replace permanent frame checks; IDs removed from the full dashboard and window close release row controllers.

Native `SessionColumn` snapshots skip columns outside the viewport. The viewport check includes card-motion bounds. This changes paint only. Row allocation, input, focus, and accessibility stay unchanged. Scroll and layout invalidate skipped snapshots when their columns enter the viewport.

On composited X11, the existing realize hook disables GTK4 compositor-feedback frame sync when the surface API is available. Wayland and noncomposited displays stay unchanged. Native springs, the renderer, and reduced-motion rules stay unchanged. This GTK4 X11 backend API is deprecated and has no replacement. The fallback frame clock may run at about 60 Hz.

Browser rows stay keyed by chat ID, and their cache is bounded by current dashboard IDs. Provider and project groups are retained for the visible list. A title change updates the existing row without rebuilding rows or listeners. Reconciliation preserves in-flight opens, retained focus, and project collapse choices. A `304` skips list reconciliation while age labels still update once a minute through the existing refresh cycle.

The Codex, Claude, and normalization modules have one mode. The ASB view has no token, quota, artifact, model-service, or governance data, except the usage-limit reset time of a stopped session. The Codex reader makes no network request, reads no `auth.json`, and writes no file. `AMC_CODEX_RESET_CREDITS` has no effect. There is only the Claude Desktop Code reader for Claude. Metadata fingerprints reuse unchanged records. Source events can invalidate caches even when file stats do not change. Local Codex and Claude signal and lifecycle caches retain up to 5000 keys per enabled store. Shared values are held once. Codex lifecycle checkpoints use the same source ownership, including rollouts outside the store folder. Local metadata caches retain up to 5000 Claude records and 32 Codex records per store. Disabling, removing, or changing a store prunes its local cache owners; values shared with an active store stay available. Standalone readers keep one bounded 5000-key signal scope. Owner tracking permits up to eight registered source stores plus that bounded standalone scope. The Claude directory index has a 32-root limit. Concurrent Claude profiles with the same `projectsDir` share one directory signature check. They also share cached root, subagent, and Workflow lookup maps. Multiple migrated child candidates still get current modification times. Stale in-flight index reads cannot restore invalidated or removed cache entries. Remote response-cache retention is separate from this local source ownership.

The OpenCode reader keeps one result per enabled OpenCode source. On each load it compares the size and modification time of `opencode.db` and `opencode.db-wal` with the cached values, because a WAL append does not change the main file. Equal values reuse the result with no query. The file watcher on the OpenCode folder accepts only `opencode.db` and `opencode.db-wal` events and only marks the snapshot dirty; there is no OpenCode file hint. Source updates and removals clear the OpenCode cache, and disabled sources lose theirs.

The remote reader keeps at most 32 cache roots, 50,000 classified file names per root, 512 response entries, and 5000 projected session records per root. Aggregate eviction preserves only the newest selected response chain so linked updates are not lost. Raw protected storage can reach `512 × 5000` records per root; its metric reports the actual raw count. Key discovery and file-stat scans use six concurrent readers. Approved response bodies queue before allocation. Runtime body reads and worker parsing run one at a time. One lazy shared worker decodes and parses bodies, using `src/claude-remote-data.mjs` itself. Its queue has at most 512 metadata jobs; explicitly submitted async bodies have a 48 MiB aggregate limit. Encoded bodies are limited to 8 MiB and decoded bodies to 16 MiB. Unrelated cache writes do not reread old keys or bodies. Built-in zstd decoding is optional; gzip watch reads work on older supported Node.js versions. The first remote load has worker startup overhead. An idle worker is unreferenced. A 30-second deadline or worker error rejects pending work. Shutdown rejects queued work immediately and stops old scan producers. After watcher cleanup, server close requests a graceful worker exit. Active bounded parsing is allowed to return before the worker closes. A replacement worker starts only after the old worker exits. This avoids forced termination during native decompression. A hung native parse can block worker exit and replacement. Tests retain the pure synchronous parser. This adds no runtime file or dependency.

Codex tails start at 64 KiB and grow to 256 KiB. On the first read of a log that is larger than the tail, ASB does not parse each line of the full log when the tail gives the lifecycle state. It searches the raw bytes before the tail for a real question call (a `function_call` named `request_user_input` or `request_user_input_async`) and reads lines only from such a call until the question state is clear again. The results are the same as a full scan. A log whose tail has no lifecycle event still gets the full scan. Lifecycle and question recovery can scan full logs with bounded memory and append checkpoints held in memory. Later reads continue from the saved offset. Claude transcript tails have an 8 MiB limit and use six concurrent reads. Larger Claude logs recover complete lifecycle and Agent links with bounded memory. Signal reads keep an in-memory state and offset, including loaded questions and metadata. On growth, the reader checks the file identity and a 64-byte boundary guard. A match permits a read from the saved offset. A valid final JSON record without a newline is visible, but the next append rereads that line. Truncation, replacement, equal-size changes, and detected boundary rewrites trigger recovery. The append guard assumes earlier bytes stay unchanged when a file grows. Pending permission entries retain only the newest 5000. Local-command prefixes do not start new work. Broad no-path invalidation reuses unchanged lifecycle data, while targeted and equal-size rewrites retain safe invalidation. Unchanged child logs use cached signals. Retained history can still make cold reads slow. ASB writes no transcript or work-metric cache.

### Known X11 frame-rate limitation

No safe app-only 240 Hz fix was found on the tested stack. Keep Python and the current X11 workaround. Resize lag remains unresolved. See [the investigation report](docs/benchmarks/x11-frame-timing-2026-10-13.md) for methods, results, failed trials, and restoration checks.

The 2026-10-13 tests used ASB `1.7.0`, Debian `13`, GNOME/Mutter `48.7`, GTK `4.18.6`, Libadwaita `1.7.6`, NVIDIA `550.163.01` with RTX `4070 SUPER`, and GNOME X11. Monitors were primary landscape `1920×1080 @ 239.76 Hz` and portrait `1080×1920 @ 60 Hz`. All trials used 149 visible synthetic rows with unchanged UI/features.

The installed realize hook disables compositor-feedback frame synchronization. GTK reported `16667 µs` (about 60 Hz), consistent with [GTK's fallback](https://docs.gtk.org/gdk4/method.FrameClock.get_refresh_info.html). Restoring native synchronization on a fresh test surface gave these results from 105 adjacent frame intervals on the original layout:

| Interval | Median (ms) | 95th percentile (ms) |
| --- | --- | --- |
| Paint | 0.703 | 1.778 |
| After-paint to `FRAME_DRAWN` receipt | 16.154 | 32.784 |
| Receipt to next paint | 0.036 | 0.083 |

The buffer held 214 protocol messages, with zero drops/errors. These are frame callbacks, not physical display FPS. The driver/Mutter/message-delivery split is unproven.

[Mutter's refresh selection](https://github.com/GNOME/mutter/blob/48.7/cogl/cogl/cogl-xlib-renderer.c#L419-L440) uses greatest overlap; equal-area ties follow output-name order. The 60 Hz portrait came first here. A temporary `900×1600` portrait mode changed reported refresh to `4171 µs` (about 240 Hz), but callbacks stayed near 33 ms (about 30 Hz). Default EGL, GLX with app-local VSync off, and GLX primary-device selection stayed near 33 ms. `GDK_DEBUG=no-vsync` did not improve changed-scroll cadence and used about 90% of one CPU core. Settings were restored. These trials support no permanent resolution or bypass-flag change.

After a distro, desktop, GTK, or driver change, record the exact stack, X11/Wayland, renderer/context, and monitor rates. Use the same synthetic data and window size on the high-rate monitor. Compare scroll, Drawer, resize, frame intervals, and CPU. Add a single-monitor versus mixed-monitor comparison, not yet done. Distinguish callbacks from display FPS. Verify all input, actions, and accessibility before removing the workaround. A distro change alone is not a proven fix.

## API and trust boundary

ASB makes no model calls and sends no messages. When ASB Bridge is installed, a message that it delivers starts a turn in the receiving app.

ASB uses `createAsbServer` from `src/asb-server.mjs`. It allows the view assets, dashboard, source events, app-source settings, agent status and UI reports, known-session open, ASB Read/Unread, Discard/Keep, drawer in/out, pins, pin movement, Persistent unread settings, and the window palette. Other API routes are not exposed.

Actions require the local Host and a matching Origin. App-source changes also need the app source token when the server has one (see below). Session IDs must be in the scanned list. Read/Unread, pin/unpin, and drawer in/out accept an empty JSON object. Persistent unread accepts only a `persistentUnread` boolean. Pin movement accepts `up`/`down`, or a known pinned target with `before`/`after`. Session actions accept no client commands, paths, or URLs.

Read APIs (dashboard, including forced refresh, sources, events, and agent status) accept an absent Origin or the exact local Origin. Sec-Fetch-Site must be absent, `same-origin`, or `none`. Cross-site reads return 403 before source loading. These access checks run before the `ETag` comparison of the dashboard. Native no-header requests and normal address-bar navigation remain supported; asset routes keep their existing behavior.

Malformed request URLs return 400 without stopping the server. A malformed session ID on an ASB state-action route gives 400. Malformed JSON gives 400 on every action route. The open reply has no `resumeCommand`. The `?refresh=` alias is not available; use `?force=1`. The dashboard reply has no `performance.notifications`. It has the counters `performance.dashboard.watchWalks` and `performance.dashboard.notModified`. The native HTTP client converts incomplete responses and bad status lines into its normal failure callback, including incomplete source-error bodies. Failure text does not include partial response data, and loading/action latches can recover.

| App-source route | Contract |
| --- | --- |
| `GET /api/sources` | `revision`, registered sources, colors, compatibility profile metadata, chat counts/status, and the eight-source limit. Needs no token. |
| `POST /api/sources` | `{source: {...}}` with full `provider`, `label`, `dataDir`, `launcher`, and `enabled` fields. Include `id` to edit; omit it to add. Optional `color` uses `#RRGGBB`; optional `showMarker` is boolean. Claude can include `projectsDir`. Needs the header `X-ASB-Source-Token` when a token is set. Returns `changed`, `savedRevision` (the revision of this request's write), and the current `revision`, `sources`, and `maxSources` read after the dashboard scan; another client's save during the scan can make `revision` differ from `savedRevision`. |
| `POST /api/sources/<id>/remove` | Empty JSON object; default source removal is rejected. Needs the header `X-ASB-Source-Token` when a token is set. Returns the same fields as `POST /api/sources`: `savedRevision` is this removal's write, and `revision` and `sources` are the current settings. |
| `POST /api/threads/<id>/discard-result` | Empty JSON object; forces a source scan and requires a known Working row. Arms its current task once. |
| `POST /api/threads/<id>/keep-result` | Empty JSON object; uses the normal cached lookup and clears a known row's Discard arm without a forced scan. |
| `POST /api/threads/<id>/drawer-in` | Empty JSON object; same access checks as `mark-read`. Puts the row in the drawer. Gives 400 unless the row is unread with no question and no required action. Replies `{ changed, threadId, thread }`. |
| `POST /api/threads/<id>/drawer-out` | Empty JSON object; same access checks as `mark-read`. Takes the row out of the drawer. Gives 400 unless the row is in the drawer. Replies `{ changed, threadId, thread }`. |

| `POST /api/threads/<id>/mute` | Empty JSON object; same access checks as `mark-read`. Turns Mute on for a known row. Replies `{ changed, threadId, thread }` with `thread.muted: true`. |
| `POST /api/threads/<id>/unmute` | Empty JSON object; same access checks as `mark-read`. Turns Mute off for a known row. Replies `{ changed, threadId, thread }` with `thread.muted: false`. |

Each dashboard row has the boolean fields `drawer` and `muted`. A drawer row has `unread: false`. The phone gateway does not forward `mute` or `unmute`; the phone and the web view show no Mute control. `mark-read` and `mark-unread` clear the drawer flag. The web view (`npm start`) shows a drawer row as read. It has no Drawer pill and no drawer actions.

Providers are `codex` and `claude-desktop-code`. Paths must be absolute local paths; additional launchers must be supported installed executables. Source updates reject raw command, argument, environment, and unknown fields. They use the same Host and Origin protection as session actions.

A local program that is not a browser can send Host and Origin itself, and a source change can set the launcher that ASB runs. For this reason, the engine creates one random token for each run and publishes it in `service.json`; the launcher gives it to the window. When a token is set, `POST /api/sources` and `POST /api/sources/<id>/remove` need the header `X-ASB-Source-Token`. Without it, the reply is 403 with `Use app source actions from the ASB window.` The native client sends the token on protected settings, palette, and UI report requests when `ASB_SOURCE_TOKEN` is set. A server started with `npm start` has no token. Source writes then have only the Host and Origin checks; agent routes reject access.

### Local agent interface

`asb agent status` reads runtime metadata and current revisions. `asb agent sources list`, `get <id|name>`, `add --file <json-file|->`, `update <id|name> --file <json-file|->`, and `remove <id|name>` manage sources through the running instance. An exact id wins; otherwise one source with that name is selected, and equal names give `source_ambiguous`. `asb agent peers` is read-only: it reads the source list from the running instance, then the owned `<pid>.json` records in each real Claude registry folder (`sessions` next to each Claude transcript folder, and `~/.claude/sessions`). It checks the process owner, state, and recorded start time before and after it reads `CLAUDE_CONFIG_DIR` and `CODEX_HOME` from that process, and maps the agent home to exactly one source name or `unknown`. It reports only projected record fields and never connects to a peer socket. Each command supports `--json`. JSON input is at most 64 KiB, contains editable fields only, and rejects unknown fields. Update merges supplied fields into current settings. An equal update, a repeated Add for the same physical store with matching supplied settings, or Remove for an absent ID is unchanged. A different registration for an existing store requires Update. Writes use quoted `If-Match`; conflicts require a fresh read. See [the user guide](ASB.md#local-agent-commands).

Both routes below require a nonempty configured token and the exact `X-ASB-Source-Token`; they return `Cache-Control: no-store`. Status uses the read-origin checks. UI reports use the action Host/Origin checks and the normal body limit.

| Loopback route | Contract |
| --- | --- |
| `GET /api/agent/status` | `apiVersion: 1`, `pid`, `mode` (`service` or `desktop`), `appVersion`, `rootDir`, `sourcesPath`, saved `sourcesRevision`, actual cached dashboard `backendRevision` (or `null`), and `ui.clients`. No token is returned. |
| `POST /api/agent/ui` | Exact body `{clientId,sourcesRevision,profilesRevision,profilesVisible,dirty}`. `clientId` is a UUID; revisions are `null` or 64 lowercase hex characters; flags are strict booleans. Replies `{received:true,reportedAtMs}`. The server keeps at most 16 recent clients and expires reports after 45 seconds. |

Native clients report received dashboard and Profiles revisions, visibility, and dirty state on changes and about every 25 seconds through the existing poll. Reports include no unsaved field contents. CLI write verification checks saved settings and the cached backend separately, then reports UI as `verified`, `pending`, `dirty`, or `not-open`. UI verification requires a recent report with the target dashboard revision and, if Profiles is visible, its target table revision. After a write, the report must also be at least as new as the write request. These are acknowledgments of received state, not proof of visual display. UI status is reported separately from command success, which requires saved and backend verification.

### Loopback phone and service routes

These routes exist only when the server has a phone gateway (the engine). `npm start` has no gateway, so they give 404. All of them need the header `X-ASB-Source-Token` when a token is set, also the GET routes; else the reply is 403. GET routes use the read checks above. POST routes use the action Host and Origin checks and strict bodies (exact keys, else 400). Replies have `Cache-Control: no-store`.

| Loopback route | Contract |
| --- | --- |
| `GET /api/phone` | Gateway `status()`: `enabled`, `bindAddresses`, `port`, `addresses` (`address`, `interface`, `kind`), `listening` (`kind`, `address`), `running`, `error`, `warning`, `fingerprint`, `devices` (ID, name, times), and `pairing.expiresAtMs`. It never has a token, token hash, or pairing code. |
| `POST /api/phone/settings` | `{"enabled":bool,"bindAddresses":[str],"port":int}`. `bindAddresses` has 0 to 8 different addresses, and each must be in `addresses` now. When `enabled` is true, it must have at least one address. The port must be 1024 to 65535 and not the ASB port. Saves, restarts the listener, and replies with `status()`. |
| `POST /api/phone/pairing` | `{}`. Needs a running listener. Replies `{ uri, expiresAtMs }`. |
| `POST /api/phone/devices/<id>/revoke` | `{}`. `<id>` is 12 lowercase hex. Removes that phone and replies with `status()`. |
| `GET /api/service` | `{ service, pid }`. `service` is true only in the engine. `findRunningService()` uses it. |
| `POST /api/engine/stop` | Engine only. Needs a nonempty token, the action Host and Origin checks, and the exact body `{}` (else 400). Replies `{"stopping":true}`, then the engine stops and exits with code 0. The phone gateway never forwards it. |

### Palette route

The native window shares its resolved palette, so the phone can use the same colors. This route exists also when the server has no phone gateway.

| Loopback route | Contract |
| --- | --- |
| `POST /api/palette` | Body exactly `{"mode","colors"}`. `mode` is `gnome` or `custom`. `colors` has exactly `background`, `text`, `accent`, `muted`, `divider`, `success`, and `warning`, each `#RRGGBB`. Else 400. Uses the action Host and Origin checks, and needs the header `X-ASB-Source-Token` when a token is set (else 403). The server saves the colors in lowercase and replies `{ changed }`. A change sends the normal `dashboard` event. |

`GET /api/dashboard` has the top-level field `palette`: the last saved `{ mode, colors }`, or `null` before the first publish. The field is part of the `ETag` content, so a palette change gives a new tag. In GNOME mode the window sends the `native_colors()` values with the GNOME `success_color` and `warning_color`. In Custom mode it sends the saved custom colors, with `success` and `warning` equal to `accent`. The window sends at start, after Apply theme, after Reset to GNOME, and after a GNOME dark style or accent change. It sends only a palette that is different from the last good send. A failed send writes one line to stderr, and the next apply tries again.

### Phone gateway

`createPhoneGateway` in `src/phone-gateway.mjs` makes the phone listeners, separate from the loopback server. It is off by default. `listPhoneAddresses()` lists each usable IPv4 address as `{ address, interface, kind }`, sorted by kind (`lan`, `zerotier`, `tailscale`), then by interface name:

| Kind | Rule |
| --- | --- |
| `tailscale` | The interface name starts with `tailscale` and the address is in `100.64.0.0/10`. |
| `zerotier` | The interface name starts with `zt` and the address is RFC 1918 private (`10/8`, `172.16/12`, `192.168/16`). |
| `lan` | Any other interface with an RFC 1918 private address. |

A `100.64.0.0/10` address on an interface that is not Tailscale is never listed, because carrier NAT and mobile hotspots also use this range. Loopback and public addresses are never listed. The gateway never binds `0.0.0.0`.

When `enabled` is true, the gateway listens on each address in `bindAddresses` that is listed now, all on the same port (default `4630`), with the same certificate and the same handler. It skips a selected address that is not listed now, and `status().error` names it; the other addresses still listen. A port in use also goes in `status().error`. `running` is true when at least one listener listens. `status().listening` lists the listeners that listen now.

`phone.json` is schema 2 with `bindAddresses`. A schema 1 file (`bindAddress`) loads as schema 2 (an empty `bindAddress` gives `[]`), and the next save writes schema 2.

TLS uses `node:https` with `minVersion: 'TLSv1.3'` on every listener. On first start, `openssl req` (run with `execFile`, no shell, 20-second timeout) creates a self-signed P-256 certificate for ten years. The pin is the SHA-256 of the full certificate, as 64 lowercase hex characters. When `openssl` fails, phone access stays off with `ASB cannot create the phone certificate. Install openssl.` The request timeout is 15 seconds, the header timeout is 10 seconds, and the keep-alive timeout is 65 seconds. Every reply has `cache-control: no-store` and `x-content-type-options: nosniff`.

The gateway handles each request in this order:

1. It closes the socket when the remote address is not allowed on that listener (also as `::ffff:a.b.c.d`). A `lan` or `zerotier` listener allows loopback and RFC 1918 callers. A `tailscale` listener allows `100.64.0.0/10` and RFC 1918 callers. No listener allows public callers.
2. Throttle: 20 auth failures (401) or pair failures from one address in 60 seconds give `429` for 60 seconds. The map keeps at most 256 addresses.
3. A bad URL gives 400. A path outside the allowlist gives 404. A wrong method gives 405.
4. Each route except pairing needs `Authorization: Bearer <token>`, with a 43-character base64url token. The gateway compares its SHA-256 with each saved hash in constant time. No match gives 401.
5. POST bodies are limited to 64 KiB (413).

| Gateway route | Action |
| --- | --- |
| `POST /phone/v1/pair` | Body exactly `{"code","deviceName"}`. Gives the phone a new token. |
| `GET /phone/v1/hello` | `{ api: 1, asbVersion, deviceId, serverName, addresses, port }`. `addresses` is `[{ kind, address }]` for the listeners that listen now. The app updates its saved address list from it. |
| `GET /phone/v1/dashboard` | Proxy to `GET /api/dashboard`. Only the query `force=1` passes. |
| `POST /phone/v1/threads/<id>/<action>` | Proxy to the same loopback thread route. `<action>` is `open`, `mark-read`, `mark-unread`, `pin`, `unpin`, `move-pin`, `discard-result`, `keep-result`, `drawer-in`, or `drawer-out`. |
| `POST /phone/v1/settings/unread` | Proxy to `POST /api/settings/unread`. |

The proxy calls `127.0.0.1:<ASB port>` and sets `Host` itself. POST also gets the local `Origin` and `content-type: application/json`. Only `If-None-Match` passes from the phone; cookies, `Authorization`, and other headers do not. Only `content-type` and `etag` come back from the loopback reply. Every dashboard reply that the loopback server answers has `Vary: Accept-Encoding`. The gateway's own error replies (401, 405, 429, 502) do not. When the phone accepts gzip in `Accept-Encoding` (`gzip` with a q-value above 0, or `*` with a q-value above 0 when `gzip` is not listed) and the loopback status is 200, the gateway streams the body through gzip and sets `Content-Encoding: gzip`. The `ETag` stays the same. A 304 reply has no body and no `Content-Encoding`. Other routes are not compressed. The Android app sets no `Accept-Encoding` header, so OkHttp sends `gzip` and decompresses the reply. A loopback error after a gzip reply starts closes the connection. A failed loopback request gives 502, and the proxy timeout is 30 seconds. The loopback server applies its normal checks. The gateway cannot reach `/api/agent/*`, `/api/sources`, `/api/phone*`, `/api/service`, `/api/palette`, or `/api/events`.

Pairing: `createPairing` makes one code of 20 random bytes (base64url). It is valid for 10 minutes and for one use. A new code replaces the old one, and 8 wrong codes void it. The QR link is `asb://pair?v=2&a=<list>&p=<port>&f=<fingerprint>&c=<code>&n=<host name>`. `<list>` is the listening addresses as comma-separated `kind:address` items in the kind order above (for example `lan:192.168.50.4,zerotier:10.147.17.4,tailscale:100.101.102.103`), URL-encoded as one value. Version 1 links had `h=<one address>`. The Android app reads this link from its own scanner (Scan QR code: CameraX preview and ZXing decode on the phone, CAMERA permission asked on first use), from the phone camera or any QR scanner app (a VIEW intent filter for `asb://pair`), or from a pasted link. All of them only fill the Check the PC screen; the user compares the fingerprint and pairs. The scanner-open state is in `PairingViewModel`, so a rotation keeps it open, and a result after Back or unpair is ignored. A good pair request saves a new device with a 256-bit random token and replies with the token once. The PC saves only the SHA-256 of the token. The device limit is eight (409). The device name is trimmed, has no control characters, and has at most 64 characters. `lastSeenAtMs` is saved at most once per 10 minutes per phone, and on stop. Revoke removes the device, so its token gives 401 at once.

## Local writes

| Default location | Purpose |
| --- | --- |
| `~/.local/state/asb/pending.json` | ASB attention, pins, Persistent unread, current-task Discard marks, drawer marks, and Mute. |
| `~/.local/state/asb/palette.json` | The last palette from the window, for the dashboard `palette` field, mode `0600`. The server reads it at start. A bad file gives `palette: null` and one stderr warning; the next publish replaces it. |
| `~/.config/asb/layout.json` | Width, view, and optional boolean `showAppPills`. |
| `~/.config/asb/theme.json` | Custom colors. |
| `~/.config/asb/sources.json` | App-source IDs, labels, colors, dot visibility, paths, launchers, and enabled flags, with owner-only access. |
| `~/.config/asb/phone.json` | Phone access settings and paired devices with token SHA-256 values, mode `0600`. An invalid file moves to `phone.json.bad`. |
| `~/.config/asb/phone-tls/` | Phone certificate `cert.pem` and key `key.pem`, mode `0600`, folder `0700`. |
| `$XDG_RUNTIME_DIR/asb/service.json` | Shared desktop/service descriptor: schema, pid, port, and per-run source token, mode `0600`, user-owned folder `0700`. |
| `~/.config/systemd/user/asb.service` | User service unit, only after `asb service install`. |
| `~/.local/share/applications/local.asb.AgentSwitchBoard.desktop` | Per-user launcher. |
| `~/.local/share/icons/hicolor/scalable/apps/local.asb.AgentSwitchBoard.svg` | Per-user app icon. |

XDG state/config/data overrides apply. The per-user package also installs ASB under its own local data folder and adds `~/.local/bin/asb`. `~/.local/bin/asb` records `ASB_NODE` and starts the shipped `scripts/asb`. It keeps `ASB_NODE` when it is an absolute, executable regular file with no control characters; otherwise it records the current Node executable. Paths use shell quoting. If the recorded Node.js is not usable, `scripts/asb` tries `~/.local/bin/node`, `/usr/local/bin/node`, then `/usr/bin/node`. It prints a message if none is usable. ASB does not put system folders before the caller's `PATH`. It appends `/usr/local/bin:/usr/bin:/bin` and a recorded SQLite folder, so apps started from ASB keep the caller's `PATH` order. Uninstall removes the `asb/releases` and `asb` data folders when they are empty. SIGINT/SIGTERM abort package work, await pending writes and rollback, and remove only its acquired lock and staging folder. A foreign lock stays intact and the error identifies its folder. See the installer for its exact manifest. Original app stores stay read-only, with one exception: the read-only SQLite open of the Codex state database can create `-wal` and `-shm` side files next to it. The files `pending.json.bad`, `sources.json.bad`, and `phone.json.bad` can appear next to their originals.

Only when the user runs them with targets, `asb bridge install` and `asb bridge uninstall` change Codex plugin configuration through the `codex` CLI. They copy or remove the Codex `$bridge` and Claude Code `/bridge` skill folders. Without targets, they show usage and change nothing.

The optional bridge plugin runs inside Codex. It writes per-task state under `<CODEX_HOME>/plugin-state/asb-bridge/` and registry rows under `<Claude home>/sessions/`. The Claude home is `$CLAUDE_CONFIG_DIR` or `~/.claude`. Uninstall keeps the per-task message history.

`asb bridge link-claude <profile-home> <shared-home>` is a separate opt-in write operation. It shares only the native `sessions` registry, which holds peer metadata and IPC authentication keys. It leaves settings, transcripts, app data, logins, provider credentials, Codex homes, and the ASB source registry separate. Both existing registry directories must be real, user-owned, and `0700`; owned `0755` and `0775` config homes are supported without a permission change. The command validates known JSON/key entries, checks conflicts before writes, copies with exclusive creation, keeps the original source in a private backup, and creates a directory link to the shared registry. A correct existing link is unchanged. Unknown files, path containment, unsafe paths, and changing source files cause refusal. Rollback restores the source when its path is free and removes only unchanged copies. A recreated source path or changed copy is kept and reported, with the backup. Install and uninstall keep the link and all registry data. Native Claude Code `2.1.303` follows this link and has no separate registry override; this internal behavior has no compatibility promise. See [the setup guide](bridge/README.md#link-claude-profiles).

## Checks and release

```bash
npm test
python3 test/asb_native_logic_test.py
npm run build
cd android && ./gradlew --no-daemon testDebugUnitTest lint assembleDebug assembleRelease
```

The first two commands do not launch the ASB window. `npm test` needs no `sqlite3` command and no environment variable. Launcher checks use isolated HOME/XDG/source folders, `ASB_SYSTEM_INSTALL=1`, and `ASB_PYTHON=/bin/true` to verify busy/free ports without GTK or icon registration. Display-free data checks share the synthetic GTK fixtures through AST extraction without importing GTK. Native widget tests are separate and need a GTK display with synthetic fixtures. Use them only when UI testing is in scope. Do not use real session stores for public media or test captures.

The Android build needs JDK 21 and the Android SDK; see `android/README.md`. The phone gateway certificate tests skip when `openssl` is not on `PATH`. The service tests use a fake `systemctl` and do not change the real user session.

The root tests skip TypeScript files. After bridge changes, run `cd bridge && bun run check && bun test && bun run build`, and commit `bridge/dist/`. When you change a shipped bridge file, change the version in `bridge/package.json` and `bridge/.codex-plugin/plugin.json` together. Codex caches an installed plugin by version.

Native SSE retains its connection/header timeout but removes the live read timeout after validated stream headers; close shuts down blocked reads. Row ages use relative text for all elapsed days, and empty `XDG_CONFIG_HOME` falls back to the home config folder. Row and tooltip indicator CSS share the same shape rules and keep their existing roles/sizes.

Native RGB conversion limits extended GNOME color channels to `0..255` before it formats `#RRGGBB`. This keeps theme editor values and phone palettes valid. Native tests use `Cantarell 11` for exact pixel checks and a separate larger-font check for row packing; production font and minimum row sizes stay unchanged.

The source build produces `asb_1.8.1_all.deb`, `asb-1.8.1-linux.tar.gz`, and `SHA256SUMS` in `dist/`. The portable root is `asb-1.8.1/` with `./install.sh`. See [release notes](docs/releases/v1.8.1.md) for upgrades and check limits. Public demo assets use synthetic session names and folders. The current demo source shows four app switches; the existing README video link stays unchanged. Remotion build dependencies are separate from the ASB runtime.

The published `1.8.1` baseline passed 272 Node tests, 87 native logic tests, and one focused GTK toolbar test on an isolated hidden Xephyr display with Cairo and synthetic data. The full GTK widget suite did not run. Real profile edits were not tested. Resize lag on X11 remains unresolved. That release had no new FPS measurement. See [1.8.1 release notes](docs/releases/v1.8.1.md) for its check limits. Earlier performance samples and their limits remain in the [1.6.1 release notes](docs/releases/v1.6.1.md) and [1.6.0 release notes](docs/releases/v1.6.0.md).

The earlier unreleased Drawer build had thirteen GTK widget tests. An earlier unreleased Drawer build was tested on one X11 machine, before the performance changes. All thirteen tests passed on a nested test display for that earlier build. The desktop display run was made before the thirteenth test was added: eleven tests passed and the pointer test was skipped. One test uses real pointer clicks through `xdotool`. It runs only when `xdotool` is installed and `DISPLAY` is `:9` or `:10` (a nested test display), so that it cannot move the pointer of a desktop; in other cases it is skipped. The tests set the Adwaita icon theme, because their pixel checks read icon pixels and the highest alpha of an icon is different in each icon theme. Four of them had expectations older than the 1.3.0 layout and were repaired after the `1.5.0` release. The 68px Comfortable row assertions hold with that machine's font; with Adwaita Sans or Noto Sans the rows are 70px. Two tests check row packing with another font and with overlay scrolling off. For ASB `1.5.0`, card motion and the wheel spring were also measured on that display with synthetic rows. No Debian `apt install` was run. Native pixel fidelity remains unverified. See the [publication record](docs/OPEN_SOURCE_PLAN.md) for verified release checks.
