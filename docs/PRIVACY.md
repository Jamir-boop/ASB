# ASB privacy

ASB runs locally. Its default native and browser launch commands read no login credentials, make no model calls, send no telemetry, and make no network requests outside loopback, with one exception: when you use the Usage view (the Usage window or the Usage screen of the phone), the engine downloads the LiteLLM price list from GitHub. This is an HTTPS GET of a public file (`raw.githubusercontent.com`, then `api.github.com` when that fails). It sends no ASB data, but GitHub sees your IP address and the request. After a good download, ASB downloads the list again at most once in 24 hours; after a failed download, it tries again at most once a minute while you use the Usage view. The optional phone gateway is off by default. When you turn it on, it accepts connections from paired phones and from the members of an optional machine group, on the private LAN, ZeroTier, or Tailscale addresses that you select.

This document covers `npm start`, `npm run desktop`, the packaged `asb` launcher, and the optional `asb service`. The optional bridge and the optional Android companion are described below.

## What ASB reads

- The latest Codex `~/.codex/state_N.sqlite`, opened read-only.
- `~/.codex/session_index.jsonl` for chat names.
- Matched local Codex read marks in `.codex-global-state.json`. ASB uses only the creator identity and local host that match the database. It does not use credentials to identify the account.
- Matched `~/.codex/sessions/**/rollout-*.jsonl` lifecycle, activity, completion, and question signals.
- Claude Desktop Code `local_*.json` metadata under `$XDG_CONFIG_HOME/Claude/claude-code-sessions`, or `~/.config/Claude/claude-code-sessions` on Linux.
- Associated Claude transcripts under `~/.claude/projects` for lifecycle and completion signals.
- Live Claude session records in the `sessions` folder next to each Claude transcript folder, for a current permission or question wait, for the desktop approval guard, and for Claude Code CLI cards. On Linux, the server checks that the process is alive in `/proc/<pid>/stat`. On Windows, it checks that the PID is alive and that the record's message pipe is in the list of named pipes (`\\.\pipe\`); it reads no pipe and keeps no pipe names. The server keeps only the session IDs, name, status, `waitingFor`, status time, folder, kind, entrypoint, `startedAt`, and `bridgeSessionId` (only a `cse_` or `session_` ID). It never reads a process environment; only the opt-in `asb agent peers` command reads its two home variables. It never opens the `.key` files in that folder.
- `logs/main.log` in each Claude app profile folder, for desktop approval waits. ASB reads only the `Emitted tool permission request`, `Received permission response for`, `LocalSessions.respondToToolPermission: requestId=`, `Permission request <id> for <tool> aborted`, and `willQuit: handler fired` line forms. It keeps only the request ID, session ID, tool name, and time, in memory only. It starts with at most the last 1 MiB, then reads from the byte after the last complete line. It keeps no log text; a partial last line is read again later.
- Claude Code CLI transcripts under `~/.claude/projects` whose `entrypoint` is `cli`, with activity in the last 7 days or a live session. They become view-only cards with the same lifecycle signals as desktop transcripts. For the title, ASB reads only `customTitle` of `custom-title` records and `agentName` of `agent-name` records. It never reads `bridge-session` records (they hold account IDs) and never uses prompt text as a title.
- For the background counts, from the subagent logs of a chat (`<session>/subagents/agent-<id>.jsonl`) and the logs of its workflow runs (`<session>/subagents/workflows/<run>/*.jsonl`): only the task ID and the time of a background command start (a tool result text that starts with `Command running in background with ID:` or `Monitor started (task`, and the `expires in` time of a Monitor), and the task ID, the status, and the time of the end markers (a task notification, a Monitor expiry, a `TaskStop` result). In the root log, the `content` of a `queue-operation` enqueue record can be a message that you typed: ASB reads it only when it starts with `<task-notification>`, and keeps only the task ID and the time of an end. ASB never keeps command text or output.
- The `<cross-session-message>` delivery records in these transcripts. For the card message lines, ASB reads only the opening tag and keeps only the `from-session` or `from` sender ID and the record time. For the Messages view, ASB reads Claude Code transcripts changed in the last 30 days: the body of each delivery record (the text between the opening tag and the last closing tag) and `from-name` or `name`, and the `message` and the target (`to` or `session_id`) of each `SendMessage` tool call of the sending session. Its cache keeps no text: per message only the IDs, the time, the status, the name from the message (at most 120 characters), a hash of the text (the first 16 hex digits of SHA-256), and the place of the line in the file. ASB reads the text again, from that one line, only for the newest 200 messages of a reply and the newest 60 messages of a thread that you open. It never keeps the socket address.
- Usage-limit numbers. From Codex session logs, ASB uses only `codex_error_info` of `task_complete` errors, and `used_percent` and `resets_at` of `rate_limits.primary` and `rate_limits.secondary` in `token_count` records. It never uses the error message. From Claude transcripts, it uses only `isApiErrorMessage`, `error`, and `quotaLimits.resetsAt` of assistant records. It never uses the limit message text or account and plan data. The view gets only the reset time.
- ASB Bridge databases under `<CODEX_HOME>/plugin-state/asb-bridge/`, opened read-only. For the card message lines, ASB reads only `peer_id`, `direction`, `status`, `kind`, and `created_at` of incoming (`in`) rows from the last two minutes. For the Messages view, it also reads the message rows of the last 30 days (also in the OpenCode bridge state folder): `id`, `peer_id`, `direction`, `status`, `status_reason`, and `created_at` of rows of kind `message`. It keeps only a fixed reason word, never the `status_reason` text. It also selects `text` of these rows to make the text hash, and keeps only the hash. It selects `text` again only for the newest 200 messages of a reply and the newest 60 messages of a thread that you open. It never selects `peer_address`. From the `runtime` row it reads the counts and times of open approvals and questions (`approvals`, `questions`, `approval_at`, `question_at`), and from the `receiver` row the `pid` and `proc_start` of the receiver process.
- The OpenCode database `opencode.db` in `$XDG_DATA_HOME/opencode`, or `~/.local/share/opencode`, opened read-only. For the Usage view, ASB also reads the `opencode-<name>.db` files in the same folder. ASB reads the table list (`sqlite_master`), the column names of `session_v2` and `session_message`, and these columns of `session_v2`: `id`, `parent_id`, `title`, `slug`, `directory`, `time_created`, `time_updated`, `time_suspended`, `time_idle`, `idle_outcome`, `time_viewed`, and `time_archived`. From `session_message`, it reads only `session_id` and `time_created`, and for the background counts of shells and background subagents one count query whose SQLite JSON functions select, inside `data`, the type, name, `status`, `metadata.status`, and shell ID of shell tool parts, the type, name, `background` input, and child session ID of subagent tool parts, and the source and shell ID of shell end records: ASB receives only a count and the earliest start time per session. For a root session whose `idle_outcome` is `failed`, one more query selects only `error.type` inside `data` of its newest assistant message, to find a usage-limit stop (`provider.quota`). For the Usage view, it also reads the column names of the `message` table, and the message ID, the token counts, the model, and the time of assistant messages from `session_message` and `message` (`id`, `type`, `time_created`, and values of `data` that SQLite JSON functions such as `json_extract` select). It uses the message ID only to count each message once. It never selects the whole `data` value, which holds prompts and answers. It never reads `auth.json` or the `account`, `control_account`, `credential`, or `kv` tables.
- The records of the ASB agy hook (`~/.local/state/asb/agy/<conversation-id>.json`), for the rows, status, and focus of Antigravity CLI (agy) sessions. ASB reads its own hook records and the agy process (its PID and start time). For a quiet foreground agy row in a verified kitty window, ASB reads the visible screen at most every 30 s to check for an interrupt above the empty prompt. It keeps no screen text and does not send or log it. This code reads no agy login, no conversation database, no `history.jsonl`, and no transcript text: it only stats the transcript file under `~/.gemini/antigravity-cli` for its modification time. It calls no Google service and no agy local API. The hook record keeps no prompt, answer, or model text (the field list is in the write table below). The Usage reader is separate: it reads the Antigravity `*.db` files.
- Token usage for the Usage view and the usage ledger: the engine reads it 10 minutes after it starts and then every hour, and also when you use the Usage view, a group member asks for the usage of this machine, you export the usage, or the engine saves a usage backup. In Codex rollouts the `token_count` counts, the model of `turn_context`, and the first `session_meta` (to skip the copied records of a forked session); in Claude transcripts the `usage` counts, the model, and the message and request IDs of assistant records. The compressed Codex rollouts (`*.jsonl.zst`) give the same values. In Grok `updates.jsonl` files, only `turn_completed` lines: `sessionUpdate`, the `usage` counts (`inputTokens`, `outputTokens`, `cachedReadTokens`, `cacheCreationTokens`, and `modelUsage` by model), the time (`agentTimestampMs` or `timestamp`), `sessionId`, and `prompt_id`. In Pi session files: `id`, `type`, `timestamp`, and the `role`, `provider`, `model`, `responseModel`, and `usage` counts (`input`, `output`, `cacheRead`, `cacheWrite`) of message and usage lines; ASB does not use the `usage.cost` values. In the Antigravity `*.db` files (opened read-only): the table list, and the `idx` and metadata blobs of `gen_metadata`, `steps`, and `trajectory_metadata_blob`; from the blobs only the model name and ID, the times, the token counts, and the usage IDs. ASB uses the session, prompt, entry, and usage IDs only to count each record once. ASB reads only the newest 10,000 transcript files. It parses only the lines that hold these markers, and it keeps only the time, the model, and the token counts; it keeps no message text.
- Approved Claude session-list and watch response bodies in `Cache/Cache_Data` for remote Code metadata. The reader uses only `https://claude.ai/v1/code/sessions` and `/watch`, with validated cache boundaries and bounded decoding. It does not use HTTP headers, cookies, authentication endpoints, or remote transcript-event bodies.
- ASB's own local state, layout, and theme settings.
- `asb doctor` and `asb setup` (Linux) read only `/etc/os-release`, `/run/ostree-booted`, ASB's user unit and autostart entry (to see which autostart is installed), the `PATH` folders (to find programs), a few environment variables (`HOME`, `PATH`, `BUN_INSTALL`, `ASB_PYTHON`, the `XDG_*` folders, and `DBUS_SESSION_BUS_ADDRESS`), the output of `openssl version`, the output of `xdg-mime query default x-scheme-handler/codex` and `x-scheme-handler/claude` (the names of the desktop files that handle the `codex:` and `claude:` links), `/etc/ufw/ufw.conf`, the output of `firewall-cmd --state` and `firewall-cmd --get-zone-of-interface=<interface>`, the runtime file `service.json` with `GET /api/service` and `GET /api/phone` of the local engine (doctor only, to find the engine and the selected addresses; setup uses its own reply), and the output of a Python probe. The probe reports the Python, PyGObject, GTK, Libadwaita, and GLib versions, cairo support, whether `qrcode` imports, and whether `org.kde.StatusNotifierWatcher` has an owner on the session bus. The install and the window use the same probe. The window start keeps the last good result of the probe in `board-check.json` (see the file list below), and `asb doctor` and `asb setup` never use it. `asb service install` (which `asb setup` runs) also reads `XDG_CURRENT_DESKTOP` and `DESKTOP_SESSION`, and asks `systemctl --user show-environment` and `systemctl --user is-active graphical-session.target` to find the autostart mode. Doctor and setup print install and firewall commands and never run them; they call no `sudo`, `doas`, `pkexec`, `rpm-ostree`, `transactional-update`, package manager, or firewall change (only the read-only queries above). On Windows, they read only the `PATH` folders and `PATHEXT` (to find programs), `USERPROFILE` and `BUN_INSTALL` (to find Bun), `ASB_PYTHON`, the Windows version, whether `C:\msys64\usr\bin\pacman.exe` exists, the output of `reg query` for the `ASB` Run value, and the output of the same Python probe. They print the `winget` and `pacman` commands that install MSYS2 and the window packages, and never run them.
- Registered app profiles use their selected local folders and the same readers. ASB also reads its own `sources.json` registration file. A ChatGPT-labeled source covers local Codex coding chats, not ordinary ChatGPT cloud chat history.

Log readers can examine message and tool events in memory to identify state. They keep no prompt, answer, question, or message text after they read a record (two exceptions: the first question of a pending Claude AskUserQuestion while the PC switch **Send message text to phones** is on, and the open question that the Claude Code hook gives the engine while **Answer questions from phones** is on too, see below; both stay in memory only): their caches hold times, flags, counts, IDs, text hashes, and a few metadata fields (title records, folder, model, version, branch name, and the name from a session message). The ASB view receives no question body, answer text, raw transcript, or credential. The Messages view receives the text of the messages that sessions send each other (see below). ASB does not write to original app stores. One exception applies: the read-only SQLite open of the Codex state database can create `-wal` and `-shm` side files next to it. The read-only open of an ASB Bridge database or the OpenCode database can do the same.

## What ASB displays locally

Chat IDs, names, folders, app names, source IDs/names/colors, archive state, execution state and reason, update time, working time, usage-limit reset time, subagent count, app links, and ASB attention/pin marks can appear in the local API or view. Compatibility profile numbers remain API metadata and are not visible. The source table also shows registered data and launcher paths, enabled flags, and chat count/status. These fields can still identify private work. Use synthetic data for public media and reports.

Each local row can also have a full session reference (`asb:1/<machine-id>/<source-id>/<scope-tag>/<type>:<app-session-id>`) and its source scope tag. The reference and the tag hold no title, folder, path, address, or key. The tag is a keyed digest (HMAC-SHA-256 with a key that comes from the machine identity secret), so a person cannot guess a folder or a user name from it. The machine group sends the tag of each row to the other members; it never sends the identity secret or the key.

For the card message lines, the view gets only pairs of row IDs (sender and receiver) and the message times. It gets no message text, sender name, or address. The Messages window also gets the message IDs, the status group and a fixed reason of each message, and the session titles. It gets the text only of the newest 60 messages of a thread that you open, also of messages between sessions of other machines of the group (at most 2,000 characters each), and the name from a message for a session that is not a card (at most 120 characters). It gets no address. Message text goes to paired phones only when you turn on the switch **Send message text to phones** in Preferences > Phone; it is off by default. Only while this switch is on, the Claude log readers (Desktop Code and Code CLI) also keep the first question text of a pending AskUserQuestion, at most 300 characters, in memory and never on disk, and ASB sends it only to paired phones (`questionText` of a waiting row in the phone dashboard). A wrap-up question keeps no text. When the switch goes off, ASB drops these texts. While the switch is on, a local program that asks `GET /api/dashboard?text=1` on 127.0.0.1 also gets the question text (a program of the same user can read the transcripts anyway). Codex, Codex CLI, and OpenCode rows get no question text. The Usage window gets the token counts and the costs per machine, app, model, and hour or day.

Working, Waiting, Idle, and Unknown are local observations. A completion dot is not proof of unread state in the original app. Read/Unread and pins belong only to ASB.

Remote cache observations can be incomplete or old. ASB uses the newest response and exact cursor-linked updates, and warns when no full list is cached. It does not fetch sessions or use a login. Remote records can supply an observed unread mark and explicit worker state. Missing or stale state gives Unknown. Raw participants, account IDs, configuration, bridge aliases, and action bodies stay outside the view payload.

`XDG_STATE_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, and `XDG_CACHE_HOME` override these base folders. The Pending state and source settings files have owner-only access; `sources.json` uses `0600`. They store no chat title, message body, or question text. When ASB cannot use one of these two files in full, it moves the old file to `pending.json.bad` or `sources.json.bad` before it saves a new one. An older `.bad` file is replaced. First use can register the known ChatGPT Personal profile when `sources.json` is absent and its local store and installed launcher exist. Disabling or removing a source keeps its files and saved ASB marks/settings. Per-user installation also copies the app into ASB's own data folder and creates `~/.local/bin/asb`. Uninstall removes the `asb/releases` and `asb` data folders when they are empty. The launcher contains local runtime and install paths. The installation manifest records versions and managed file hashes.

Only when you run `asb agent claude-hook install`, ASB writes one hook entry into the `settings.json` of each Claude profile that it reads (or of `--config-dir <dir>`): `hooks.PermissionRequest` with the matcher `*` and the command `<installed launcher> agent claude-wait` (it replaces the older `AskUserQuestion` entry). Other keys stay. The first change keeps `settings.json.asb-backup` next to the real file: a copy of the old settings content, its `env` block included, with the same mode. ASB keeps the backup, also after `remove`. `asb agent claude-hook remove` deletes only that entry. This is the only ASB write to a Claude config file, and `asb uninstall` does not remove the entry. The engine keeps the questions and approvals that the hook gives it, and the phone answers, in memory only, never in a file or a log. With the hook installed, Claude Code runs the ASB hook client at each permission dialog, also with the approve switch off. The client gets the full tool input on stdin and sends only the card lines to the engine on loopback; with the switch off or no paired phone, the engine replies `{ wait: false }` and keeps nothing.

Only when you run `asb agent agy-hook install`, ASB writes one `asb` hook key into `~/.gemini/config/hooks.json`: the `SessionStart`, `PreInvocation`, `Stop`, `PreToolUse`, and `PostToolUse` events, the last two with the matcher `^ask_question$`. Other keys stay. The first change keeps `hooks.json.asb-backup` next to the real file, a copy of the old content with the same mode. `asb agent agy-hook remove` deletes only the `asb` key. It also writes the `title` key (`asb agent agy-title`) into `~/.gemini/antigravity-cli/settings.json` unless you have your own `title` setting, keeps `settings.json.asb-backup` on the first change, and `remove` deletes only ASB's `title` key. Each hook command has a shell fallback that prints the neutral reply when the client prints nothing, so a failed hook does not deny `ask_question`. The hook client writes the record (above) and contacts the local engine only on `PreToolUse` of `ask_question`, where it sends the question text and options to `POST /api/agent/wait` on loopback; the engine keeps them in memory only while **Answer questions from phones** is on and a phone is paired, and sends them to the paired phone, as for Claude. For OpenCode 2 choice forms, the ASB Bridge plugin similarly sends the question text and options to the local engine on loopback (kept in memory only while the answer switch is on and a phone is paired), and reads `$XDG_STATE_HOME/opencode/service.json` (verified to belong to the same process PID and a loopback URL) to send the phone answer to OpenCode's local form reply route (`POST /api/session/:sessionID/form/:formID/reply`). ASB runs `kitty @ focus-window` only when you select a live agy row whose kitty has remote control; it reads the kitty socket and window ID from the record. kitty remote control is a kitty setting that you turn on yourself. A process that can connect to the kitty socket can do all that kitty remote control allows, not only focus.

`asb bridge install --agy` installs the stdio bundle under `~/.local/share/asb-bridge/agy` and uses `agy mcp add` to register it. ASB does not edit `mcp_config.json` directly. If that file exists, ASB keeps one private copy (`mcp_config.json.asb-backup`, `0600`) and prints only config key names and SHA-256 digests. `asb bridge uninstall --agy` uses `agy mcp remove` and removes the bundle and runtime mailbox. The Bridge keeps message history in `~/.local/state/asb-bridge/agy`, not in an agy store.

On Linux, an incoming message can wait in `$XDG_RUNTIME_DIR/asb-agy-mailbox` on the runtime tmpfs (directory `0700`, file `0600`). Only the `Stop` hook for its own conversation reads the file. The hook client contacts the local engine only at `PreToolUse` of `ask_question`, to show the question on a paired phone. It removes the file at the next eligible Stop. The receiver can also withdraw the file before kitty delivery, at 60 min, or when the session ends. If a process dies without cleanup, uninstall or end the login session to remove the runtime folder. A Stop does not deliver a file past its 60 min deadline. The Stop path delivers every input kind, including idle notices, and each one starts a model turn on your agy account, as in Codex and OpenCode. In a session started with `--dangerously-skip-permissions`, a message delivered through Stop can run tools with no agy permission prompt.

Claude Code 2.1.330 holds a peer message for your review when the receiving Claude session runs in bypass mode and the sender does not state the same permission mode. An agy sender states no mode, so a Bridge message from agy to a Claude session in bypass mode waits in that Claude session until you approve it. ASB Bridge gets no notice of the hold: the row of the sent message stays `socket-written`. To deliver the messages of all your sessions in all modes, set `"crossSessionInbound": "accept"` in the Claude `settings.json` (`/config`: "Messages from your other sessions"). Then messages from any sender reach Claude with no review, also in a session that runs commands without asking.

Checked live once with agy 1.5.15 (2026-11-23): `list_sessions` through MCP, and one message delivered at Stop. Tests use fakes for withdrawal at 60 min, `unknown` outcomes, two receivers, and release from hold.

Kitty typing is on after `asb bridge install --agy` for agy sessions in a kitty with remote control on a file socket. ASB reads the prompt screen in memory only and types into that kitty window. Kitty typing accepts a framed message of at most 8 lines and 500 characters. For a longer message, ASB types one fixed line into the idle agy prompt (`[ASB Bridge] A peer message is waiting. It arrives when this turn ends. Reply with only OK.`), with no peer data, and the message arrives through the Stop hook at the end of that turn. A long message costs two model turns on your agy account. If ASB cannot verify the typed line, it does not press Return, and the message waits for the next Stop. If ASB cannot verify the pasted text, it does not press Return. The text stays in the agy prompt as a draft. The receiver records `unknown` and sends no delivery receipt. In a session started with `--dangerously-skip-permissions`, a message typed this way can run tools with no agy permission prompt. `asb bridge uninstall --agy` turns off kitty typing. Checked live once with agy 1.5.15 (2026-11-23): ASB typed and submitted one message through kitty. A typed draft kept a second message out of the prompt. The paste check refused while the "Allow calling this tool?" dialog showed. The live check also covered pasting `@` and `/`. Tests use fakes for other kitty cases. agy shows "Allow calling this tool?" for each Bridge tool call unless you allow that tool always. The MCP allow prompt with `--dangerously-skip-permissions` is not tested.

On Windows, the same files use other folders. `%APPDATA%\asb` holds the files of `~/.config/asb`. `%LOCALAPPDATA%\asb\state` holds the files of `~/.local/state/asb` and the engine output in `engine.log` (the output of the engine start before it in `engine.log.1`). `%LOCALAPPDATA%\asb\run` holds `service.json` and `stopped.json`. The Claude and Codex hook clients and ASB Bridge read `service.json` for the loopback source token. The default hook launcher is `%APPDATA%\npm\asb.cmd`. The hooks keep backups next to the original settings files, as on Linux. `%LOCALAPPDATA%\asb\cache` holds the reader positions file. ASB limits these four folders to your Windows user with `icacls`. The ASB window writes its compiled code (no user data) in `%LOCALAPPDATA%\asb\cache\pycache`; `asb engine uninstall` does not remove it. The usage cache and the price list are in `%LOCALAPPDATA%\asb\cache\usage`, the usage ledger in `%APPDATA%\asb\usage\usage-ledger.json` (with `usage-tiers.json` next to it), the usage backup settings in `%APPDATA%\asb\usage\usage-backup.json`, the usage backups in `%APPDATA%\asb\usage\backups`, and the window sizes in `%APPDATA%\asb\activity-windows.json`. The ASB window start also saves `board-check.json` (the same content as on Linux, no chat data) in `%LOCALAPPDATA%\asb\cache`; `asb engine uninstall` does not remove it. On Windows, the ASB window reads `GSK_RENDERER` and `GDK_DEBUG`. When `GSK_RENDERER` is empty or not set and `GDK_DEBUG` does not contain `dcomp`, it sets `GSK_RENDERER=cairo` for its own process. On Linux, the window reads `GDK_BACKEND`, `WAYLAND_DISPLAY`, `DISPLAY`, `GSK_RENDERER`, and `GDK_DISABLE`; on X11, when the last two are empty or not set, it sets `GSK_RENDERER=cairo` and `GDK_DISABLE=gl,vulkan` for its own process. Its child programs inherit these variables, as on Windows. The phone certificate folder holds `cert.pfx` (the certificate and its private key), `pfx-pass` (the random passphrase of `cert.pfx`), and `cert.cer` (the public certificate). Windows PowerShell creates them and removes its temporary copy from the user certificate store. `asb engine install` and `asb setup` write the `ASB` value in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, which holds the PowerShell command that starts the tray with the paths of ASB and `node.exe`. `asb engine uninstall` removes it. `asb engine install` and `asb setup` also write the Start menu link `ASB.lnk` (it opens the ASB window), and `asb engine uninstall` removes it when ASB made it. ASB never changes the Windows firewall; `asb setup` only prints a rule that you can run.

ASB writes no search index, review job, notification store, quota history, or work-metric cache. It writes the token usage cache and the usage ledger (above) after the first usage read: 10 minutes after the engine starts, or before that when you use the Usage view, a group member asks for the usage of this machine, you export the usage, or the engine saves a usage backup. `asb usage export` writes a file with the data of the ledger for all machines that this machine knows: the machine IDs and names, and the hourly token counts by app and model. It writes the file with mode `0600` and sends it nowhere; you copy it. **Export…** in Preferences > Usage writes the same file where you choose. Each day the engine also writes a usage backup with the same data (see above), and it sends the backups nowhere. `asb usage import` and **Import…** read only such a file. The Codex reader makes no network request and reads no `auth.json`. Its source readers keep bounded caches in memory. The engine also saves reader positions in `~/.cache/asb/readers/positions.json`. After a restart, the engine uses them to read only the new bytes of a Codex session log or of a Claude transcript that is larger than 8 MiB, to skip the tail read of a Codex log that did not change, and to skip the Claude Desktop cache entries that are not a session list or watch. The file has no message text, title, question text, tool input or output, path, URL, cursor, entry name, or folder name. It has keyed digests of the log paths, of the last 64 bytes that the engine read, and of the names of the cache entries. The key comes from the machine identity secret and stays in memory. The engine reads a log from the start, and opens all cache entries, when the file is missing, damaged, or from a different ASB reader version, or when a record does not agree with its log or its cache folder. The file has at most 5000 Codex records, 5000 Claude records, and 8 MiB. It also has at most 5000 Codex tail results and 5000 groups of cache entries. You can delete it at any time.

Source colors are ASB settings in the same schema `1` file. They change only the local identity marker, not original app styles, data, sign-ins, or attention state. Source IDs remain the identity; color does not merge chats. Source names remain available in tooltips, search, and accessible descriptions.

## Optional ASB Bridge

ASB Bridge runs inside Codex and OpenCode 2. It also runs as a stdio MCP server for agy on Linux. It stores the text of peer messages in per-task SQLite files under `<CODEX_HOME>/plugin-state/asb-bridge/`. ASB does not upload them. The same files hold the counts and times of the open approvals and questions of the task (no request text, tool input, or title); the OpenCode plugin keeps the request IDs only in memory. The engine reads the counts and times to show Waiting. A message that the bridge delivers starts a turn in the receiving app. The receiving app uses its own model and network settings.

The OpenCode plugin writes the same class of state as the Codex plugin: its own state folder, registry rows and key files, socket files, and messages added to OpenCode sessions through the plugin API. This is the only OpenCode session write path. It never edits `opencode.json`, the OpenCode database, or `auth.json`. To answer an OpenCode question form from the phone, the plugin reads `$XDG_STATE_HOME/opencode/service.json` (else `~/.local/state/opencode/service.json`), the file that OpenCode writes for its own local server. It uses the file only when the file is a regular file of your user and its `pid` is the OpenCode process that the plugin runs in. It takes the loopback `url` and the server `password` from it and sends one form reply to that server (`POST /api/session/<session>/form/<form>/reply`, Basic authentication). It keeps the password only in memory for that request and sends it nowhere else.

On Linux and Windows, `list_sessions` asks the local ASB engine for the full session reference of each listed session, or the reason code when a send cannot use one. The model of the Codex task then sees these references: the machine IDs of this machine and of the other members, the source IDs, the scope tags, and the session types. The reply has no path, PID, socket, or token.

To show the ASB Bridge state in Preferences > Profiles and Preferences > Machines, or when a group member asks, the engine runs `asb bridge status --json` in a child process. It runs it only when a request asks, at most once in 60 s (Refresh in Profiles runs it again at once), and has no timer of its own. While Preferences > Machines shows, its 5 s poll asks, so the check runs about once a minute. The command reads each `~/.codex*/config.toml` and uses only its ASB Bridge entries (the plugin, the marketplace, and the hook trust), the ASB Bridge plugin, skill, and state folders and their record files (also the bridge skill folder of each enabled Claude profile), the Claude session records in the `sessions` folder of the default Claude home (to count live receivers; it never opens the `.key` files), and on Linux the `HOME`, `CODEX_HOME`, and `PATH` values of running `codex app-server` processes (to see whether Codex finds Bun; it reads the command line of each process to find them). It keeps no other environment value and reads no message text. It runs `bun --version`, `codex --version` (with an empty temporary `CODEX_HOME`), `claude --version`, `opencode --version`, and `opencode debug paths`. When OpenCode is installed, `opencode debug paths` makes its own folders (config, data, state, and cache) if they do not exist yet. **Install** and **Update** in a profile dialog run `asb bridge install` for that profile only when you select them. `asb setup` installs ASB Bridge only for the apps that do not have it, and only when you choose a setup with the bridge.

Only when you run `asb bridge link-claude <profile-home> <shared-home>`, setup links the profile's native `sessions` directory to the selected shared registry. This shares peer metadata and local IPC authentication keys across those profiles. It does not share settings, transcripts, app data, logins, model-provider credentials, or Codex homes. Linked peers can discover and message each other, and a message can start a model turn in the receiving app. This broadens local messaging access within your user account.

The registry and the original-directory backup are private (`0700`). Setup never overwrites a target file. Unknown files and detected concurrent changes cause refusal. A failed rollback keeps and reports the original backup or changed copies when removal would risk data loss. The backup is a snapshot and does not receive later updates. Install and uninstall keep the shared registry, link, and backup. Native link behavior was checked in Claude Code `2.1.303`; it is not a published API. See [the setup and rollback limits](../bridge/README.md#link-claude-profiles).

## Optional Android companion

Phone access is off by default. You turn it on in Preferences > Phone and pair each phone with a one-time QR code. The ASB app scans the code with its own scanner, or the phone camera or any QR scanner app opens the `asb://pair` link in the ASB app. The app uses the camera only while the scanner is open, to read the pairing code. Camera frames stay on the phone and are not saved or sent. The app uses no Google Play services. ASB uses no cloud service and no relay of its own. The phone talks to the PC directly on your local network, or away from home through ZeroTier or Tailscale when you install and join one of them on the PC and the phone. These overlay networks are third-party services with their own privacy terms; ASB does not configure them. The gateway binds only the private LAN, ZeroTier, and Tailscale addresses of the PC that you select. It never binds a public address. A home network or ZeroTier address accepts only loopback and private IPv4 remote addresses. A Tailscale address accepts only Tailscale (`100.64.0.0/10`) and private IPv4 remote addresses. All traffic uses TLS 1.3. The phone pins the SHA-256 of the ASB certificate, and you compare the fingerprint during pairing.

A paired phone receives the same dashboard data as the local view: chat titles, folders, app and source names and colors, execution states, update and working times, usage-limit reset times, attention, pin, and drawer marks, and row IDs. For session messages it receives only pairs of row IDs and the message times. While the PC switch **Send message text to phones** is off, it receives no message text, question body, answer text, transcript, or credential; with the switch on, it also receives the message text of threads and the first question of a waiting Claude session (see below); with the answer switch on too, it also receives the open question of a Claude session with its options (see below). It never receives an answer text, a transcript, or a credential. The Messages and Usage screens get the counts, statuses, session titles, and token usage of the Messages and Usage views, never message text in these overviews: the gateway asks the PC for the messages with `text=0`, so the PC reads no text for the phone and leaves out the text and the names from the messages. The thread route, which has the message text, exists for the phone only while the PC owner turns on the switch **Send message text to phones** in Preferences > Phone. The switch is off by default; a paired phone can see if the switch is on, and no phone can change it. With the switch on, the PC also sends the message text of the other machines of its group to its phones. It also receives the PC host name, the ASB version, the listening addresses and port of the gateway, and the color palette of the ASB window (seven `#RRGGBB` colors and the GNOME or Custom mode). The phone can open chats on the PC and use the row actions (also mute and unmute) and Persistent unread. It cannot read or change app sources or phone settings. In a machine group, hello also gives the phone the name, addresses, port, and certificate fingerprint of each member, and the phone uses its one token with the members when the paired PC does not answer.

Each phone gets its own 256-bit random token. The PC saves only the SHA-256 of each token. The phone keeps the token in app-private storage, and the app turns off Android backup and device transfer. **Remove** in Preferences > Phone ends that phone's access at once. The pairing code works once and ends after 10 minutes. Repeated failed attempts from one address are blocked for one minute. To know which alerts are new, the app saves a baseline in its private preferences: for each row, the attention marks, the Done and Failed times, and the ID of its open question or approval (32 hex characters). It never saves the request text.

Phone notifications show the state word, the machine name, the session title, and the source name; while the switch **Send message text to phones** is on, a Needs input notification also shows the question text when expanded. The app marks them private, so a secure lock screen shows only the kind ("A session needs your answer", "A task failed", "A task hit a usage limit", or "A task is done"), with no session title, machine, or question, when the phone setting hides sensitive notification content; otherwise the lock screen shows the question too. When the switch goes off, or the question is gone, the app takes the question out of a posted Needs input notification at its next good read of the PC; until that read, for example while the phone is offline, the notification keeps it. ASB saves no question text on the phone, but Android keeps a posted notification and can give it to notification history, to apps with notification access, and to a paired watch. Anyone who unlocks the phone can see the session titles and folders in the app.

The PC switch **Answer questions from phones** is off by default and works only while **Send message text to phones** is on. With both on, a hook that you install (`asb agent claude-hook install`), and a paired phone, the phone gets the text, header, options, and option descriptions of each open question (`AskUserQuestion`) of a local Claude Desktop Code or Claude Code CLI session on Linux, and the answer that you send (the chosen labels and an Other text) goes back to the PC, which gives it to Claude Code. The app keeps them in memory only. With the answer switch on, each paired phone can answer a question of a local Claude session, and so decide what the agent does next. The app has no lock of its own: unpair a lost phone in Preferences > Phone. It is the first gateway route that changes what an agent does.

### Optional Claude Code approvals

The PC switch **Approve requests from phones** is off by default and works only while **Answer questions from phones** is on (which needs **Send message text to phones** on). With these on, the hook (`asb agent claude-hook install`, matcher `*`), and a paired phone, the phone gets an approval card when Claude Code itself shows a permission dialog. The card title has the tool name, `Allow <tool>?`, with ` for a subagent` when the request comes from a subagent, also for an MCP tool. The display lines are: for Bash, the command and its `description` (model text, cut to 500 characters); for Write, the file path and the size in characters; for Edit, the file path, the old and new lengths, and `all matches` when set; for NotebookEdit, the notebook path; for WebFetch, the URL; for WebSearch, the query (cut to 500 characters); for an MCP tool, the server name and up to 20 input key names; for every other tool (for example Read, Glob, or Task), up to 20 input key names and never the values. For a plan (`ExitPlanMode`), the card holds the plan text up to 16,000 characters and the line `After approval: Bypass permissions mode, if this session allows it`. The full tool input never leaves the hook client: no file content, no old or new string, no fetch prompt. The phone decision (allow or deny, with an optional deny note up to 500 characters) goes back to the PC, which gives it to Claude Code. The engine keeps each approval in memory only, never in a file or a log. With the approve switch on, each paired phone can allow or deny a tool, or approve a plan, of a local Claude session, and so decide what the agent does next; unpair a lost phone in Preferences > Phone. After `Approve plan` from a phone, a session that allows bypass mode runs its next tools with no dialog and no card, so a paired phone can start work that nobody approves step by step; this is the main risk of the feature.

### Optional OpenCode approvals

On main, not in a release yet. For approval text, the OpenCode plugin in ASB Bridge `0.10.0` sends only the card title and display lines. The phone gets a request ID, the tool card kind and title, and a flag that permits a note with Deny. The title is `Allow a shell command?` or `Allow a file change?`, with ` for a subagent` before `?` for a subagent. The display lines are `Command` (the full shell command) and `Folder` (the tool's `workdir` or the request folder), or `File` (the resolved path) and `Size` (the write content length, or the old and new edit text lengths). Each line has its label, text, and a flag for monospace. For a shell or edit request, the plugin asks the engine on loopback if it can hold an approval. The check sends only the provider, root session ID, and check flag. If approval is off, no phone is paired, or the engine cannot accept the request, the plugin does not read the session context. If the check passes, the plugin reads the context inside OpenCode to find the tool input. It does not send the full context, file contents, or old or new edit text to the engine or the phone.

The plugin keeps the OpenCode request ID, the root session ID, the request folder, and the wait state in memory. Its SQLite runtime row keeps only counts and the newest times for open approvals and questions, not their IDs or text. The card and the decision stay in memory in ASB. A deny note of up to 500 characters goes to OpenCode with the refusal. While **Approve requests from phones** is on, each paired phone can allow or deny an OpenCode request on the PC. Unpair a lost phone in Preferences > Phone.

### Optional Codex phone questions

ASB Bridge reads `item/tool/requestUserInput` on the shared Codex app-server for a registered thread. It sends the thread ID and the card content (headers, questions, options, and whether Other is allowed) to the local engine. It does not send a card that has a secret question or a question without options. With phone access, **Send message text to phones**, and **Answer questions from phones** on, the engine can show the card to a paired phone. The Bridge sends the selected label or allowed Other text back to Codex. ASB keeps the request and answer in memory only, not in files, logs, or group exports. Codex can keep them in its own history. Unpair a lost phone.

### Optional Codex command approvals

On Linux and Windows, run `asb agent codex-hook install` to add the optional hook for the Codex CLI and the Codex app's app-server. It is not installed by default. In the CLI, at `Hooks need review`, use `Review hooks` to find the ASB `PermissionRequest` hook. Select `Trust all and continue` only if you trust all the hooks shown. If you select `Continue without trusting`, Codex skips the hook and uses its normal approval path. The `^Bash$` matcher limits the hook to `Bash` approvals. Run `asb agent codex-hook remove` to remove it. ASB writes one entry in `<Codex home>/hooks.json` and keeps the original of an existing file as `hooks.json.asb-backup`. Removal takes out only the ASB hook. `asb agent codex-hook status`, `asb doctor`, and the local Phone settings route read `hooks.json`. The phone gateway does not send hook status or hook file contents.

While **Approve requests from phones** is on and the paired PC has seen a phone in the last 60 s, each Codex Bash command that asks for approval goes to the phone before the Codex reviewer. If you allow the command on the phone, Codex skips the reviewer. If you deny the command, Codex blocks it. Codex sends the denial and any note to the model in the tool result. The phone card stays open for 28 s (`CODEX_FIRST_MS` in `src/claude-questions.mjs`). During that time the PC shows `Running hook` with no approval buttons (the hook client stops waiting at 30 s). If the phone does not answer, Codex decides with its own settings: with `approvals_reviewer = "auto_review"`, the Codex automatic reviewer decides and can allow the command with no dialog on the PC; else Codex shows its PC dialog. Codex 0.171 asks for approval only for an escalation request (for example with `-a on-request`). A command that fails in the sandbox gives no request and no card. Each held command plays the Needs input sound on the PC and can alert on the phone, even if the automatic reviewer would allow it. The hook sends the full command and folder to the local ASB engine. The engine shows these details on the paired phone. The command, folder, and phone decision are held in memory, not saved or logged by the hook or engine. A paired phone with access can allow a command on the PC. Unpair a lost phone.

The first command of a new session can get no card. The first command after a time with no working session can reach the phone up to 30 s late, or not at all. Unlisted threads and subagent threads get no card. If two requests from one session overlap, only the newer one stays on the phone. The older one goes to the normal approval path. Until the phone app update that alerts again for a new request, a second card can come with no alert. The time with the screen off is not proven. The hook adds about 190 ms per Bash approval when it does not hold the command. A command over 4,000 characters gets no card. Codex app: the hook ran in the app's own build (`0.171.0-alpha.13`) with a loopback model fixture. The live app UI was not tested.

## Optional machine group

The machine group is off until you make one (`asb group invite`) or join one (`asb group join`). It needs network access on (`asb network enable <address>`), on the same private LAN, ZeroTier, or Tailscale addresses as phone access. Members talk directly to each other with mutual TLS 1.3. Each side pins the certificate of the other. ASB uses no cloud service and no network relay server.

Each member sends its local session rows to the other members. A row has only these fields: the row and app session IDs, the app name and label, CLI or app, the title, the folder and project name, the archive state, the update time, the subagent count, the execution state and reason, the working time, the native unread mark and read state, the question and action flags, the time of an open question or permission request, the last outcome and its times, the usage-limit reset time, the source ID, label, color, and marker settings, and the source scope tag. It also sends the native session IDs of its rows and the sender IDs and times of incoming session messages, so that message lines can join sessions on two machines. The rows do not have session message text, chat prompts, answers, transcripts, credentials, or app links. Open phone requests are an exception for question and approval text, as described below. When another member asks (`GET /peer/v1/activity`, mutual TLS) for its Messages or Usage view, for a usage export or backup, or once an hour for its usage ledger, a member also sends its activity reply: its message records (message IDs, the sender and receiver session IDs that its session rows already share, times, status groups, fixed reasons, which side of each message it has, a hash of each text, and the name from each message), the text of its newest 200 messages of the period (at most 2,000 characters each), its hourly token usage per app and model, and its scan counts. So the Messages window of each member shows the text of messages between sessions of other members. The reply never has paths, titles, costs, prompts, or answers. The member routes have no thread route. Rows from the claude.ai cache and rows from other members are not sent again. Hello replies have the machine ID and name, the group ID, the ASB version, and the listening addresses and port.

If the group has a paired phone, a session PC can include an open request ID and its card in its session export to other group members. It does this only while phone access, **Send message text to phones**, and **Answer questions from phones** are on. An approval card also needs **Approve requests from phones**. Members get the checked questions, headers, options, and option descriptions, or the checked approval title and display lines. Approval display lines can include commands, paths, or plan text. A paired PC sends only flags for phone answer readiness, the approval switch, and recent phone use. It sends no token or last-use time with those flags.

The phone PC sends selected labels, Other text, or an approval decision with an optional note only to the member that runs the session. Both routes use mutual TLS with pinned certificates. ASB keeps request and answer content in memory and does not write it to the group file or logs. The app that runs the session handles the answer as it does for a local phone reply. Not tested end to end between machines.

`~/.config/asb/group.json` (mode `0600`) stores the group ID, this machine's ID and name, each member's ID, name, certificate fingerprint, addresses, and port, removed machines, and the group phones with their names and the SHA-256 of their tokens. It never stores a token. The phone certificate is the machine identity, also in the group. A phone that you pair while in the group is added to the group list, so every member accepts its token. An invalid file moves to `group.json.bad`.

A member can ask the ASB Bridge state of this machine (`GET /peer/v1/bridge`, mutual TLS). The reply has the ASB version, the check time, and for each enabled profile its source ID, label, app, bridge state, version, live receiver count, and install command. The install command can name a folder in the home folder of this machine (for example `asb bridge install --codex-home ~/.codex-personal`). The reply has no full path, no message text, and no session data. A member cannot start an install on another machine.

Read, Unread, pins, the drawer, and Mute on a card from another machine change only the `pending.json` of the machine where you select them. ASB does not open or discard a session on another machine.

On Linux and Windows, while a group has another member and the engine finds Bun (on its `PATH`, else in `$BUN_INSTALL/bin` or `~/.bun/bin`; on Windows, `%BUN_INSTALL%\bin` or `%USERPROFILE%\.bun\bin`), the engine runs the ASB message relay (`bridge/dist/relay.js`), a local process that listens only on 127.0.0.1 and accepts only the engine's token. The relay writes proxy rows (`<home>/sessions/<pid>.json`, mode `0600`, `entrypoint: "asb-relay"`) in your local Claude config homes for sessions on other members, with the machine and session names and the status, and keeps their sockets in `$XDG_RUNTIME_DIR/asb/relay/` (else `~/.local/state/asb/run/relay/`) (on Windows, `cc-msg` named pipes). Members exchange the list of their live local sessions (session ID, name, Claude or Codex, status, and whether Claude Remote Control is on). When a local session writes a message to a proxy row, the text goes only to the member that runs the target session, over the same mutual TLS, and that member writes it to the target session's socket. ASB does not save or log the message text. The relay removes its rows when it stops. On Windows, each proxy row and each bridge receiver also has a key file (`<pid>.<hash>.key`) with a random local token next to its row, as Claude Code writes for its own sessions; ASB removes it with the row. On Windows the relay also writes the receipts of exact member sends to the receiver of the sending task; for that it reads the key file of that receiver. A Codex task with ASB Bridge sends the text of a message to another machine to the local ASB engine on `127.0.0.1`, which sends it only to the target member over mutual TLS. The engine does not log it and keeps no queue; the bridge keeps the sent text in the task's own SQLite file, as for a local send.

For an exact send by full reference to a session on another member, the engine first sends only the typed target (the source ID, the scope tag, the session type, and the app session ID) to that member, and the member answers with one reason code. Then it sends the typed target, the sender fields of a relayed message (this machine's ID, the sender session ID and name, the permission mode, and Claude or Codex), the text, the hop chain, and the time that is left (`remainingMs`). The member answers with one outcome and at most one reason code. Paths, PIDs, process start times, sockets, keys, tokens, and titles never go to another machine. The member reads its own session records and bridge `receiver` table to find the one target, and gives the process data only to its own local relay.

The receipt of an exact send goes back from the member to the sending engine as one control: the message ID, the state, and the bounded reason text of the receiver (at most 64, 1000, and 64 characters), with no message text and no destination. The sending engine keeps each attempt in memory for 30 minutes, with no text: the message ID, the member certificate fingerprint, the reference, and the receiver record of the sending task (its session ID, PID, process start time, and socket path). These stay on the sending machine. It opens only the outbox socket of that receiver, after it checks that the socket and its folder are private to this user.

## Local API and app opens

The ASB server binds only to `127.0.0.1`. `HOST` cannot change that. The optional phone gateway is a separate listener; see above. The native window and optional browser view use this local API. Source events contain a version, reason, and provider flags, with no file paths or content. Watchers do not upload files.

Session actions require the local Host, a matching Origin, a known session ID, and validated request fields. Source changes use the same Host and Origin protection and accept only source settings. When the launcher starts ASB, source changes also need its per-run token in the header `X-ASB-Source-Token`. A server started with `npm start` has no token. Local paths and installed app launchers are validated. Raw commands, arguments, environment fields, and arbitrary URLs are rejected. Other local programs under your account can still access local metadata.

The optional GNOME top-bar extension runs in GNOME Shell. It reads the private runtime descriptor for the port and the token, with the same file checks as the launcher. Without the token, it reads `GET /api/events` and `GET /api/panel` on `127.0.0.1`: the three counts, at most 6 sessions that need you and 6 that work (ID, title, app name, provider, machine number, time, and whether ASB can open it), the machines of the group (name, online, and counts), and the accent color of the board. It sends the token only to `POST /api/engine/show-window` and `POST /api/engine/stop`, never logs it, and makes no other network request. The phone gateway and the machine group never forward `/api/panel`. While it runs, it owns the session bus name `local.asb.AgentSwitchBoard.Panel`; the tray watches this name only to hide its icon.

`asb agent` reads the private runtime descriptor and uses its ASB token to inspect or change sources through loopback. It reads no app login credentials and does not print the token. The agent status route always requires a nonempty configured token. It returns the ASB version, pid, mode, root path, source settings path, and saved/backend revisions. Source revisions use normalized settings only, with no chat content or session counts; they add no stored field to schema `1` `sources.json`. Revision checks reject stale writes with `409`. `asb agent peers` reads only your own Claude session records and processes. From each live agent process it reads only the `CLAUDE_CONFIG_DIR` and `CODEX_HOME` values, to find its app home. It keeps and prints no other environment value, no peer keys or tokens, and no Codex config contents; it only checks that `~/.codex*/config.toml` exists. The output can show agent names, session IDs, pids, folders, and home paths. `asb agent resolve-session` reads only the rows that the engine already has in its cached session list, the source settings, and the machine group member list. It returns no title, folder, path, process data, or token, and it writes no state. For an exact send of ASB Bridge, the engine also reads the live session records of the sending task and the `pid` and `proc_start` of the bridge `receiver` table. It gives the process data (pid, start time, and socket path) only to the local bridge, and it writes no state.

`asb agent claude-wait` and `asb agent codex-wait` read the hook input on stdin. They send the provider, session ID, and question or approval card fields to `POST /api/agent/wait` with the ASB source token. They print only the answer for the agent. They write no file or log line. `POST /api/threads/<id>/answer` takes a reply only for the open request of that session and only while its switch is on. The phone gateway forwards it only then. It never forwards the wait routes, including the older `/api/agent/claude-wait` route.

Native UI reports contain a random client UUID, received dashboard and Profiles revisions, Profiles visibility, a dirty flag, and the server receipt time. They contain no unsaved field values. The server holds at most 16 reports in memory and expires them after 45 seconds. A window that closes sends a last report with only its client UUID, which removes its report at once. These reports confirm received state and do not prove visual display. Profiles refresh keeps unsaved edits and Add drafts; a conflict requires loading the saved source before another save. The phone gateway exposes neither the agent routes nor source or phone administration routes.

Selecting a row opens a validated `codex:` or `claude:` app link. Default sources use the existing URL handler. A registered profile can use its installed launcher; ASB passes one validated URI through detached `spawn`, without a shell. The launched app runs independently after dispatch; ASB does not wait for or stop it. ASB does not change sign-ins, credentials, app data, or default handlers. The original app can make its own network requests under its own settings. ASB does not send it a prompt, answer a question, cancel a task, or change its read state.
