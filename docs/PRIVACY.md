# ASB privacy

ASB runs locally. Its default native and browser launch commands read no login credentials, make no model calls, send no telemetry, and make no network requests outside loopback. The optional phone gateway is off by default. When you turn it on, it accepts connections from paired phones and from the members of an optional machine group, on the private LAN, ZeroTier, or Tailscale addresses that you select.

This document covers `npm start`, `npm run desktop`, the packaged `asb` launcher, and the optional `asb service`. The optional bridge and the optional Android companion are described below.

## What ASB reads

- The latest Codex `~/.codex/state_N.sqlite`, opened read-only.
- `~/.codex/session_index.jsonl` for chat names.
- Matched local Codex read marks in `.codex-global-state.json`. ASB uses only the creator identity and local host that match the database. It does not use credentials to identify the account.
- Matched `~/.codex/sessions/**/rollout-*.jsonl` lifecycle, activity, completion, and question signals.
- Claude Desktop Code `local_*.json` metadata under `$XDG_CONFIG_HOME/Claude/claude-code-sessions`, or `~/.config/Claude/claude-code-sessions` on Linux.
- Associated Claude transcripts under `~/.claude/projects` for lifecycle and completion signals.
- Live Claude session records in the `sessions` folder next to each Claude transcript folder, for a current permission or question wait and for Claude Code CLI cards. The server checks that the process is alive in `/proc/<pid>/stat` and keeps only the session IDs, name, status, `waitingFor`, status time, folder, kind, entrypoint, `startedAt`, and `bridgeSessionId` (only a `cse_` or `session_` ID). It never reads a process environment; only the opt-in `asb agent peers` command reads its two home variables. It never opens the `.key` files in that folder.
- Claude Code CLI transcripts under `~/.claude/projects` whose `entrypoint` is `cli`, with activity in the last 7 days or a live session. They become view-only cards with the same lifecycle signals as desktop transcripts. For the title, ASB reads only `customTitle` of `custom-title` records and `agentName` of `agent-name` records. It never reads `bridge-session` records (they hold account IDs) and never uses prompt text as a title.
- The opening tag of each `<cross-session-message>` delivery record in these transcripts. ASB keeps only the `from-session` or `from` sender ID and the record time. It never keeps the message body, `from-name`, or the socket address.
- Usage-limit numbers. From Codex session logs, ASB uses only `codex_error_info` of `task_complete` errors, and `used_percent` and `resets_at` of `rate_limits.primary` and `rate_limits.secondary` in `token_count` records. It never uses the error message. From Claude transcripts, it uses only `isApiErrorMessage`, `error`, and `quotaLimits.resetsAt` of assistant records. It never uses the limit message text or account and plan data. The view gets only the reset time.
- ASB Bridge databases under `<CODEX_HOME>/plugin-state/asb-bridge/`, opened read-only. ASB reads only `peer_id`, `direction`, `status`, `kind`, and `created_at` of incoming (`in`) rows from the last two minutes. It never selects `text` or `peer_address`.
- The OpenCode database `opencode.db` in `$XDG_DATA_HOME/opencode`, or `~/.local/share/opencode`, opened read-only. ASB reads the table list (`sqlite_master`), the column names of `session_v2` and `session_message`, and these columns of `session_v2`: `id`, `parent_id`, `title`, `slug`, `directory`, `time_created`, `time_updated`, `time_suspended`, `time_idle`, `idle_outcome`, `time_viewed`, and `time_archived`. From `session_message`, it reads only `session_id` and `time_created`. It never reads `auth.json`, the `account`, `control_account`, `credential`, or `kv` tables, or `session_message.data`, which holds prompts and answers.
- Approved Claude session-list and watch response bodies in `Cache/Cache_Data` for remote Code metadata. The reader uses only `https://claude.ai/v1/code/sessions` and `/watch`, with validated cache boundaries and bounded decoding. It does not use HTTP headers, cookies, authentication endpoints, or remote transcript-event bodies.
- ASB's own local state, layout, and theme settings.
- `asb doctor` and `asb setup` (Linux) read only `/etc/os-release`, `/run/ostree-booted`, ASB's user unit and autostart entry (to see which autostart is installed), the `PATH` folders (to find programs), a few environment variables (`HOME`, `PATH`, `BUN_INSTALL`, `ASB_PYTHON`, the `XDG_*` folders, and `DBUS_SESSION_BUS_ADDRESS`), the output of `openssl version`, the output of `xdg-mime query default x-scheme-handler/codex` and `x-scheme-handler/claude` (the names of the desktop files that handle the `codex:` and `claude:` links), `/etc/ufw/ufw.conf`, the output of `firewall-cmd --state` and `firewall-cmd --get-zone-of-interface=<interface>`, the runtime file `service.json` with `GET /api/service` and `GET /api/phone` of the local engine (doctor only, to find the engine and the selected addresses; setup uses its own reply), and the output of a Python probe. The probe reports the Python, PyGObject, GTK, Libadwaita, and GLib versions, cairo support, whether `qrcode` imports, and whether `org.kde.StatusNotifierWatcher` has an owner on the session bus. The install and the window use the same probe. The window start keeps the last good result of the probe in `board-check.json` (see the file list below), and `asb doctor` and `asb setup` never use it. `asb service install` (which `asb setup` runs) also reads `XDG_CURRENT_DESKTOP` and `DESKTOP_SESSION`, and asks `systemctl --user show-environment` and `systemctl --user is-active graphical-session.target` to find the autostart mode. Doctor and setup print install and firewall commands and never run them; they call no `sudo`, `doas`, `pkexec`, `rpm-ostree`, `transactional-update`, package manager, or firewall change (only the read-only queries above). On Windows, they read only the `PATH` folders and `PATHEXT` (to find programs), `USERPROFILE` and `BUN_INSTALL` (to find Bun), `ASB_PYTHON`, the Windows version, whether `C:\msys64\usr\bin\pacman.exe` exists, the output of `reg query` for the `ASB` Run value, and the output of the same Python probe. They print the `winget` and `pacman` commands that install MSYS2 and the window packages, and never run them.
- Registered app profiles use their selected local folders and the same readers. ASB also reads its own `sources.json` registration file. A ChatGPT-labeled source covers local Codex coding chats, not ordinary ChatGPT cloud chat history.

Log readers can examine message and tool events in memory to identify state. They keep no prompt, answer, or question text after they read a record: their caches hold times, flags, counts, IDs, and a few metadata fields (title records, folder, model, version, and branch name). The ASB view receives no question body, answer text, raw transcript, or credential. ASB does not write to original app stores. One exception applies: the read-only SQLite open of the Codex state database can create `-wal` and `-shm` side files next to it. The read-only open of an ASB Bridge database or the OpenCode database can do the same.

## What ASB displays locally

Chat IDs, names, folders, app names, source IDs/names/colors, archive state, execution state and reason, update time, working time, usage-limit reset time, subagent count, app links, and ASB attention/pin marks can appear in the local API or view. Compatibility profile numbers remain API metadata and are not visible. The source table also shows registered data and launcher paths, enabled flags, and chat count/status. These fields can still identify private work. Use synthetic data for public media and reports.

Each local row can also have a full session reference (`asb:1/<machine-id>/<source-id>/<scope-tag>/<type>:<app-session-id>`) and its source scope tag. The reference and the tag hold no title, folder, path, address, or key. The tag is a keyed digest (HMAC-SHA-256 with a key that comes from the machine identity secret), so a person cannot guess a folder or a user name from it. The machine group sends the tag of each row to the other members; it never sends the identity secret or the key.

For session messages, the view gets only pairs of row IDs (sender and receiver) and the message times. It gets no message text, sender name, or address.

Working, Waiting, Idle, and Unknown are local observations. A completion dot is not proof of unread state in the original app. Read/Unread and pins belong only to ASB.

Remote cache observations can be incomplete or old. ASB uses the newest response and exact cursor-linked updates, and warns when no full list is cached. It does not fetch sessions or use a login. Remote records can supply an observed unread mark and explicit worker state. Missing or stale state gives Unknown. Raw participants, account IDs, configuration, bridge aliases, and action bodies stay outside the view payload.

`XDG_STATE_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, and `XDG_CACHE_HOME` override these base folders. The Pending state and source settings files have owner-only access; `sources.json` uses `0600`. They store no chat title, message body, or question text. When ASB cannot use one of these two files in full, it moves the old file to `pending.json.bad` or `sources.json.bad` before it saves a new one. An older `.bad` file is replaced. First use can register the known ChatGPT Personal profile when `sources.json` is absent and its local store and installed launcher exist. Disabling or removing a source keeps its files and saved ASB marks/settings. Per-user installation also copies the app into ASB's own data folder and creates `~/.local/bin/asb`. Uninstall removes the `asb/releases` and `asb` data folders when they are empty. The launcher contains local runtime and install paths. The installation manifest records versions and managed file hashes.

On Windows, the same files use other folders. `%APPDATA%\asb` holds the files of `~/.config/asb`. `%LOCALAPPDATA%\asb\state` holds the files of `~/.local/state/asb` and the engine output in `engine.log`. `%LOCALAPPDATA%\asb\run` holds `service.json` and `stopped.json`. `%LOCALAPPDATA%\asb\cache` holds the reader positions file. ASB limits these four folders to your Windows user with `icacls`. The ASB window writes its compiled code (no user data) in `%LOCALAPPDATA%\asb\cache\pycache`; `asb engine uninstall` does not remove it. The ASB window start also saves `board-check.json` (the same content as on Linux, no chat data) in `%LOCALAPPDATA%\asb\cache`; `asb engine uninstall` does not remove it. On Windows, the ASB window reads `GSK_RENDERER` and `GDK_DEBUG`. When `GSK_RENDERER` is empty or not set and `GDK_DEBUG` does not contain `dcomp`, it sets `GSK_RENDERER=cairo` for its own process. The phone certificate folder holds `cert.pfx` (the certificate and its private key), `pfx-pass` (the random passphrase of `cert.pfx`), and `cert.cer` (the public certificate). Windows PowerShell creates them and removes its temporary copy from the user certificate store. `asb engine install` and `asb setup` write the `ASB` value in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, which holds the PowerShell command that starts the tray with the paths of ASB and `node.exe`. `asb engine uninstall` removes it. `asb engine install` and `asb setup` also write the Start menu link `ASB.lnk` (it opens the ASB window), and `asb engine uninstall` removes it when ASB made it. ASB never changes the Windows firewall; `asb setup` only prints a rule that you can run.

ASB writes no search index, review job, notification store, quota history, token cache, or work-metric cache. The Codex reader makes no network request and reads no `auth.json`. Its source readers keep bounded caches in memory. The engine also saves reader positions in `~/.cache/asb/readers/positions.json`. After a restart, the engine uses them to read only the new bytes of a Codex session log or of a Claude transcript that is larger than 8 MiB, to skip the tail read of a Codex log that did not change, and to skip the Claude Desktop cache entries that are not a session list or watch. The file has no message text, title, question text, tool input or output, path, URL, cursor, entry name, or folder name. It has keyed digests of the log paths, of the last 64 bytes that the engine read, and of the names of the cache entries. The key comes from the machine identity secret and stays in memory. The engine reads a log from the start, and opens all cache entries, when the file is missing, damaged, or from a different ASB reader version, or when a record does not agree with its log or its cache folder. The file has at most 5000 Codex records, 5000 Claude records, and 8 MiB. It also has at most 5000 Codex tail results and 5000 groups of cache entries. You can delete it at any time.

Source colors are ASB settings in the same schema `1` file. They change only the local identity marker, not original app styles, data, sign-ins, or attention state. Source IDs remain the identity; color does not merge chats. Source names remain available in tooltips, search, and accessible descriptions.

## Optional ASB Bridge

ASB Bridge runs inside Codex and OpenCode 2. It stores the text of peer messages in per-task SQLite files under `<CODEX_HOME>/plugin-state/asb-bridge/`. ASB does not upload them. A message that the bridge delivers starts a turn in the receiving app. The receiving app uses its own model and network settings.

The OpenCode plugin writes the same class of state as the Codex plugin: its own state folder, registry rows and key files, socket files, and messages added to OpenCode sessions through the plugin API. This is the only write path of ASB into an original app store. It never edits `opencode.json`, the OpenCode database, or `auth.json`.

On Linux and Windows, `list_sessions` asks the local ASB engine for the full session reference of each listed session, or the reason code when a send cannot use one. The model of the Codex task then sees these references: the machine IDs of this machine and of the other members, the source IDs, the scope tags, and the session types. The reply has no path, PID, socket, or token.

To show the ASB Bridge state in Preferences > Profiles and Preferences > Machines, or when a group member asks, the engine runs `asb bridge status --json` in a child process. It runs it only when a request asks, at most once in 60 s (Refresh in Profiles runs it again at once), and has no timer of its own. While Preferences > Machines shows, its 5 s poll asks, so the check runs about once a minute. The command reads each `~/.codex*/config.toml` and uses only its ASB Bridge entries (the plugin, the marketplace, and the hook trust), the ASB Bridge plugin, skill, and state folders and their record files (also the bridge skill folder of each enabled Claude profile), the Claude session records in the `sessions` folder of the default Claude home (to count live receivers; it never opens the `.key` files), and on Linux the `HOME`, `CODEX_HOME`, and `PATH` values of running `codex app-server` processes (to see whether Codex finds Bun; it reads the command line of each process to find them). It keeps no other environment value and reads no message text. It runs `bun --version`, `codex --version` (with an empty temporary `CODEX_HOME`), `claude --version`, `opencode --version`, and `opencode debug paths`. When OpenCode is installed, `opencode debug paths` makes its own folders (config, data, state, and cache) if they do not exist yet. **Install** and **Update** in a profile dialog run `asb bridge install` for that profile only when you select them. `asb setup` installs ASB Bridge only for the apps that do not have it, and only when you choose a setup with the bridge.

Only when you run `asb bridge link-claude <profile-home> <shared-home>`, setup links the profile's native `sessions` directory to the selected shared registry. This shares peer metadata and local IPC authentication keys across those profiles. It does not share settings, transcripts, app data, logins, model-provider credentials, or Codex homes. Linked peers can discover and message each other, and a message can start a model turn in the receiving app. This broadens local messaging access within your user account.

The registry and the original-directory backup are private (`0700`). Setup never overwrites a target file. Unknown files and detected concurrent changes cause refusal. A failed rollback keeps and reports the original backup or changed copies when removal would risk data loss. The backup is a snapshot and does not receive later updates. Install and uninstall keep the shared registry, link, and backup. Native link behavior was checked in Claude Code `2.1.303`; it is not a published API. See [the setup and rollback limits](../bridge/README.md#link-claude-profiles).

## Optional Android companion

Phone access is off by default. You turn it on in Preferences > Phone and pair each phone with a one-time QR code. The ASB app scans the code with its own scanner, or the phone camera or any QR scanner app opens the `asb://pair` link in the ASB app. The app uses the camera only while the scanner is open, to read the pairing code. Camera frames stay on the phone and are not saved or sent. The app uses no Google Play services. ASB uses no cloud service and no relay of its own. The phone talks to the PC directly on your local network, or away from home through ZeroTier or Tailscale when you install and join one of them on the PC and the phone. These overlay networks are third-party services with their own privacy terms; ASB does not configure them. The gateway binds only the private LAN, ZeroTier, and Tailscale addresses of the PC that you select. It never binds a public address. A home network or ZeroTier address accepts only loopback and private IPv4 remote addresses. A Tailscale address accepts only Tailscale (`100.64.0.0/10`) and private IPv4 remote addresses. All traffic uses TLS 1.3. The phone pins the SHA-256 of the ASB certificate, and you compare the fingerprint during pairing.

A paired phone receives the same dashboard data as the local view: chat titles, folders, app and source names and colors, execution states, update and working times, usage-limit reset times, attention, pin, and drawer marks, and row IDs. For session messages it receives only pairs of row IDs and the message times. It receives no message text, question body, answer text, transcript, or credential. It also receives the PC host name, the ASB version, the listening addresses and port of the gateway, and the color palette of the ASB window (seven `#RRGGBB` colors and the GNOME or Custom mode). The phone can open chats on the PC and use the row actions and Persistent unread. It cannot read or change app sources or phone settings. In a machine group, hello also gives the phone the name, addresses, port, and certificate fingerprint of each member, and the phone uses its one token with the members when the paired PC does not answer.

Each phone gets its own 256-bit random token. The PC saves only the SHA-256 of each token. The phone keeps the token in app-private storage, and the app turns off Android backup and device transfer. **Remove** in Preferences > Phone ends that phone's access at once. The pairing code works once and ends after 10 minutes. Repeated failed attempts from one address are blocked for one minute.

Phone notifications show the session title and the source name. The app marks them private, so a secure lock screen can show only "A session needs attention", according to your Android settings. Anyone who unlocks the phone can see the session titles and folders in the app.

## Optional machine group

The machine group is off until you make one (`asb group invite`) or join one (`asb group join`). It needs network access on (`asb network enable <address>`), on the same private LAN, ZeroTier, or Tailscale addresses as phone access. Members talk directly to each other with mutual TLS 1.3. Each side pins the certificate of the other. ASB uses no cloud service and no network relay server.

Each member sends its local session rows to the other members. A row has only these fields: the row and app session IDs, the app name and label, CLI or app, the title, the folder and project name, the archive state, the update time, the subagent count, the execution state and reason, the working time, the native unread mark and read state, the question and action flags, the last outcome and its times, the usage-limit reset time, the source ID, label, color, and marker settings, and the source scope tag. It also sends the native session IDs of its rows and the sender IDs and times of incoming session messages, so that message lines can join sessions on two machines. It never sends message text, prompts, answers, transcripts, credentials, or the app links. Rows from the claude.ai cache and rows from other members are not sent again. Hello replies have the machine ID and name, the group ID, the ASB version, and the listening addresses and port.

`~/.config/asb/group.json` (mode `0600`) stores the group ID, this machine's ID and name, each member's ID, name, certificate fingerprint, addresses, and port, removed machines, and the group phones with their names and the SHA-256 of their tokens. It never stores a token. The phone certificate is the machine identity, also in the group. A phone that you pair while in the group is added to the group list, so every member accepts its token. An invalid file moves to `group.json.bad`.

A member can ask the ASB Bridge state of this machine (`GET /peer/v1/bridge`, mutual TLS). The reply has the ASB version, the check time, and for each enabled profile its source ID, label, app, bridge state, version, live receiver count, and install command. The install command can name a folder in the home folder of this machine (for example `asb bridge install --codex-home ~/.codex-personal`). The reply has no full path, no message text, and no session data. A member cannot start an install on another machine.

Read, Unread, pins, the drawer, and Mute on a card from another machine change only the `pending.json` of the machine where you select them. ASB does not open or discard a session on another machine.

On Linux and Windows, while a group has another member and the engine finds Bun (on its `PATH`, else in `$BUN_INSTALL/bin` or `~/.bun/bin`; on Windows, `%BUN_INSTALL%\bin` or `%USERPROFILE%\.bun\bin`), the engine runs the ASB message relay (`bridge/dist/relay.js`), a local process that listens only on 127.0.0.1 and accepts only the engine's token. The relay writes proxy rows (`<home>/sessions/<pid>.json`, mode `0600`, `entrypoint: "asb-relay"`) in your local Claude config homes for sessions on other members, with the machine and session names and the status, and keeps their sockets in `$XDG_RUNTIME_DIR/asb/relay/` (else `~/.local/state/asb/run/relay/`) (on Windows, `cc-msg` named pipes). Members exchange the list of their live local sessions (session ID, name, Claude or Codex, status, and whether Claude Remote Control is on). When a local session writes a message to a proxy row, the text goes only to the member that runs the target session, over the same mutual TLS, and that member writes it to the target session's socket. ASB does not save or log the message text. The relay removes its rows when it stops. On Windows, each proxy row and each bridge receiver also has a key file (`<pid>.<hash>.key`) with a random local token next to its row, as Claude Code writes for its own sessions; ASB removes it with the row. On Windows the relay also writes the receipts of exact member sends to the receiver of the sending task; for that it reads the key file of that receiver. A Codex task with ASB Bridge sends the text of a message to another machine to the local ASB engine on `127.0.0.1`, which sends it only to the target member over mutual TLS. The engine does not log it and keeps no queue; the bridge keeps the sent text in the task's own SQLite file, as for a local send.

For an exact send by full reference to a session on another member, the engine first sends only the typed target (the source ID, the scope tag, the session type, and the app session ID) to that member, and the member answers with one reason code. Then it sends the typed target, the sender fields of a relayed message (this machine's ID, the sender session ID and name, the permission mode, and Claude or Codex), the text, the hop chain, and the time that is left (`remainingMs`). The member answers with one outcome and at most one reason code. Paths, PIDs, process start times, sockets, keys, tokens, and titles never go to another machine. The member reads its own session records and bridge `receiver` table to find the one target, and gives the process data only to its own local relay.

The receipt of an exact send goes back from the member to the sending engine as one control: the message ID, the state, and the bounded reason text of the receiver (at most 64, 1000, and 64 characters), with no message text and no destination. The sending engine keeps each attempt in memory for 30 minutes, with no text: the message ID, the member certificate fingerprint, the reference, and the receiver record of the sending task (its session ID, PID, process start time, and socket path). These stay on the sending machine. It opens only the outbox socket of that receiver, after it checks that the socket and its folder are private to this user.

## Local API and app opens

The ASB server binds only to `127.0.0.1`. `HOST` cannot change that. The optional phone gateway is a separate listener; see above. The native window and optional browser view use this local API. Source events contain a version, reason, and provider flags, with no file paths or content. Watchers do not upload files.

Session actions require the local Host, a matching Origin, a known session ID, and validated request fields. Source changes use the same Host and Origin protection and accept only source settings. When the launcher starts ASB, source changes also need its per-run token in the header `X-ASB-Source-Token`. A server started with `npm start` has no token. Local paths and installed app launchers are validated. Raw commands, arguments, environment fields, and arbitrary URLs are rejected. Other local programs under your account can still access local metadata.

`asb agent` reads the private runtime descriptor and uses its ASB token to inspect or change sources through loopback. It reads no app login credentials and does not print the token. The agent status route always requires a nonempty configured token. It returns the ASB version, pid, mode, root path, source settings path, and saved/backend revisions. Source revisions use normalized settings only, with no chat content or session counts; they add no stored field to schema `1` `sources.json`. Revision checks reject stale writes with `409`. `asb agent peers` reads only your own Claude session records and processes. From each live agent process it reads only the `CLAUDE_CONFIG_DIR` and `CODEX_HOME` values, to find its app home. It keeps and prints no other environment value, no peer keys or tokens, and no Codex config contents; it only checks that `~/.codex*/config.toml` exists. The output can show agent names, session IDs, pids, folders, and home paths. `asb agent resolve-session` reads only the rows that the engine already has in its cached session list, the source settings, and the machine group member list. It returns no title, folder, path, process data, or token, and it writes no state. For an exact send of ASB Bridge, the engine also reads the live session records of the sending task and the `pid` and `proc_start` of the bridge `receiver` table. It gives the process data (pid, start time, and socket path) only to the local bridge, and it writes no state.

Native UI reports contain a random client UUID, received dashboard and Profiles revisions, Profiles visibility, a dirty flag, and the server receipt time. They contain no unsaved field values. The server holds at most 16 reports in memory and expires them after 45 seconds. A window that closes sends a last report with only its client UUID, which removes its report at once. These reports confirm received state and do not prove visual display. Profiles refresh keeps unsaved edits and Add drafts; a conflict requires loading the saved source before another save. The phone gateway exposes neither the agent routes nor source or phone administration routes.

Selecting a row opens a validated `codex:` or `claude:` app link. Default sources use the existing URL handler. A registered profile can use its installed launcher; ASB passes one validated URI through detached `spawn`, without a shell. The launched app runs independently after dispatch; ASB does not wait for or stop it. ASB does not change sign-ins, credentials, app data, or default handlers. The original app can make its own network requests under its own settings. ASB does not send it a prompt, answer a question, cancel a task, or change its read state.
